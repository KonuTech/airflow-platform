<objective>
Close the walking skeleton: make the gate enforcing rather than advisory, and observe a real run
of it on this repository.

Purpose: without a branch rule, CI fails the build but does not block the merge — success
criterion 1 would be only half true. The repository is now public, which unlocks the setting that
was returning a permission error while it was private.

The rule is deliberately shaped to enforce the gate **without** locking out its only maintainer:
this project commits straight to the default branch for the ten phases that follow, so
`enforce_admins` stays false and the required approval count stays zero. A rule that made the next
phase unable to commit would not be a stricter version of this one; it would be a broken one.

Output: a required-checks rule on the default branch, documented so it can be reapplied, reversed
or removed from the repository rather than from memory, and a completed successful workflow run.
</objective>

  <action>
    Read the exact check names the workflow reports, using the repository's own run history rather
    than reading them off the workflow file — a required check name that does not match a reported
    check never becomes required, and the rule then silently blocks nothing. The two names are the
    quality-gate job and the secret-scan job.

    Apply the branch rule to the default branch by `PUT`ing to the branch-protection endpoint. Do
    not configure it only through the web interface: a setting that exists nowhere in the repository
    is not reproducible, which is the same standard this project applies to its cluster.

    The payload has exactly six top-level fields, and every one of them is a decision:

    - `required_status_checks` — `contexts` lists the two check names read above (the `Quality gate`
      job from plan 01-01 task 3 and the `Secret scan (full history)` job from plan 01-02 task 3),
      and `strict` is **`false`**. Strict mode would require a branch to be up to date with the
      default branch before merging, which is a rebase treadmill on a repository with one committer
      and no concurrent branches, and it blocks a direct push outright.
    - `enforce_admins` — **`false`**. This is the field that decides whether the rest of this
      project can be built. GSD runs this repository with `branching_strategy: "none"`, so Phases 2
      through 11 commit straight to the default branch; with `enforce_admins: true` the repository
      owner is subject to the pull-request requirement as well, direct pushes to `main` are refused,
      and every remaining phase stops. The gate stays enforcing for the pull-request path — a
      failing check still blocks that merge — while the sole maintainer keeps the bypass. Setting
      it to `true` is not a hardening improvement here; it is a self-lockout.
    - `required_pull_request_reviews` — `required_approving_review_count: 0`. A review requirement
      above zero is unsatisfiable on a single-maintainer repository: the author cannot approve their
      own pull request, so any positive count means no pull request can ever merge. Zero keeps the
      pull-request path intact without making it a dead end.
    - `restrictions` — `null`. Push restrictions are an organisation-and-team feature; on a personal
      repository the field must be explicitly null rather than omitted.
    - `allow_force_pushes` — `false`, and `allow_deletions` — `false`. These two survive
      `enforce_admins: false` as the meaningful protections that remain: the owner may push forward
      to `main`, but may not rewrite or delete its history. That is the trade this configuration
      makes, and it is the right side of it — an accidental `push --force` is the failure mode a
      solo maintainer actually has.

    Read the rule back through the API and assert, separately: that `Quality gate` is in the
    required set, that `Secret scan (full history)` is in it, and that `enforce_admins` reads back
    disabled. Existence of a rule is not the assertion; the contents are. The `enforce_admins` read-back exists so that a later well-meaning
    tightening — the kind that looks like an obvious improvement in a security review — is caught by
    a failing check rather than discovered when the next phase cannot commit.

    Write `docs/ci-branch-protection.md` recording the resulting configuration field by field, the
    exact command that applies it, the exact command that removes it (`DELETE` on the same
    endpoint), and two rationale notes. First, why `enforce_admins` is `false` — the direct-push
    requirement of every later phase — so that the next reader flipping it to `true` understands
    they are choosing to stop the project, and knows the reversal command to undo it. Second, that
    the check names are coupled to the workflow's job display names: renaming a job silently
    un-requires its check until the rule is updated. Those two are the ways this configuration
    rots — one by being tightened, one by drifting.
  </action>

| Boundary | Description |
|----------|-------------|
| Repository settings → the enforcement of every gate in this phase | Without a branch rule, every control built here is advisory |
| Local git → public GitHub | Publication is irreversible; anything in the history is world-readable from that moment |
| Workflow job names → required check names | A rename silently un-requires a check, leaving a rule that blocks nothing |
