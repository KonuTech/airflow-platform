```sql
INSERT INTO normalized.customers (
    customer_id, name, country, birth_date, event_ts,
    _run_id, _file_id, _batch_id, _source_row_number,
    _record_hash, _record_hash_version
)
SELECT DISTINCT ON (customer_id)
       customer_id::int, name, country, birth_date::date, event_ts::timestamptz,
       _run_id, _file_id, _batch_id, _source_row_number,
       _record_hash, _record_hash_version
FROM   {staging_table}
ORDER  BY customer_id, event_ts DESC, _source_row_number DESC
ON CONFLICT (customer_id) DO UPDATE
   SET name = EXCLUDED.name, country = EXCLUDED.country,
       birth_date = EXCLUDED.birth_date, event_ts = EXCLUDED.event_ts,
       _record_hash = EXCLUDED._record_hash,
       _record_hash_version = EXCLUDED._record_hash_version,
       _run_id = EXCLUDED._run_id, _file_id = EXCLUDED._file_id,
       _batch_id = EXCLUDED._batch_id, _source_row_number = EXCLUDED._source_row_number
 WHERE normalized.customers._record_hash IS DISTINCT FROM EXCLUDED._record_hash
   AND EXCLUDED.event_ts >= normalized.customers.event_ts;
```
The `DISTINCT ON (customer_id)` is REQUIRED even though `configs/datasets/customers.yaml` already declares `deduplication.strategy: business_key_latest` — PITFALLS C1: `ON CONFLICT DO UPDATE` against a source containing duplicate keys raises `ON CONFLICT DO UPDATE command cannot affect row a second time`; the guard must be structural in the SQL, not merely configured correctly upstream. `rows_loaded` is `cur.rowcount` after this statement executes — no `RETURNING merge_action()` needed this phase.

Staging table shape (04-RESEARCH.md Pitfall 9): business columns (`customer_id, name, country, birth_date, event_ts`) are `text`; the six lineage columns (`_run_id bigint, _file_id bigint, _batch_id bigint, _source_row_number bigint, _record_hash bytea, _record_hash_version smallint`) keep their REAL target types — they are populated entirely in Python, never parsed from unreliable source text, so weakening their types buys nothing and only adds cast bugs at publish time.

`normalized.customers`'s full column set is verbatim from `migrations/versions/0005_normalized_customers.py` — read it before writing `staging.py`'s `CREATE TABLE` statement, do not guess column names/types.
