## Decisions Made

- **`rlimit_as_bytes: 16777216` (16 MiB), not the pod's Kubernetes memory
  limit.** The plan's own prose said to use "the KPO ingest pod's
  configured memory LIMIT from `common_kpo_kwargs` (1Gi, i.e.
  1073741824)" -- but `common_kpo_kwargs` does not itself set a memory
  limit (resources are the caller's parameter), the ingest task's real
  configured limit is actually 4Gi, not 1Gi, and neither number can ever
  satisfy `_validate_large_profile`'s `approx_bytes > 2 * rlimit_as_bytes`
  rule for a "realistic data" ~55MB file. Followed `tests/fixtures/
  corpus.yaml`'s own already-validated precedent for this exact field
  instead (a small RLIMIT_AS-style address-space ceiling, not a
  Kubernetes resource limit) -- documented at length in the manifest's own
  comment so a future reader does not "fix" it back to a number that
  breaks manifest loading.
- **`etl_app` is the default E2E database role, `analytics_owner` the
  exception.** Per the plan's own instruction to "decide per test and
  document which" -- every assertion in this suite observes the analytical
  database through the SAME credential the real pipeline pods use, except
  where genuinely broader access is needed (none of this suite's own
  tests currently need it, but the fixture pair exists as specified).
- **SQL-only correlation to Airflow's XCom/dag_run, never the REST API or
  CLI-parsed text.** This cluster's `core.auth_manager` is `FabAuthManager`
  (verified live), which needs a login credential this suite does not
  have; the CLI's own text-output shape is not a stable contract the way
  `xcom`'s/`dag_run`'s table columns are (also verified live via `psql
  \d`).
