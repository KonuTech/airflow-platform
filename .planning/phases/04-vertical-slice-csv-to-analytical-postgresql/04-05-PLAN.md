<!-- CRITICAL ARCHITECTURAL CORRECTION -- read this before writing any code in this plan. -->

`setup.cfg`'s import-linter contract 1 (`type = forbidden`, `source_modules = dataplat`, `forbidden_modules = csv_processor`) is run by `make imports` inside `make check` — a HARD gate, and `docs/adr/0002-dataplat-core-with-csv-processor-plugin.md` records it was "observed rejecting a deliberate `import csv_processor` added to a `dataplat` module" during Phase 1. 04-PATTERNS.md's suggested location for a `SOURCE_REGISTRY` (`packages/dataplat/src/dataplat/sources/registry.py`, "registers `csv_processor.source.CsvSource` under `csv`") is WRONG: any module under `packages/dataplat/src/dataplat/` that statically imports `csv_processor` fails `make imports` immediately, full stop, regardless of whether the import is lazy/conditional/inside a function body (import-linter's static AST analysis sees it either way). Do not implement 04-PATTERNS.md's Group B `sources/registry.py` as written.

ADR-0002 itself already names the correct mechanism, in its own Decision Outcome: `csv_processor`'s `source.py` "implements the `dataplat` `Source` protocol and **registers via an entry point**." This plan implements exactly that sentence, using nothing more than the Python standard library's `importlib.metadata.entry_points` — NOT a new plugin framework (04-RESEARCH.md's Don't-Hand-Roll guidance against "a full Python entry-points plugin system" was written about `SOURCE_REGISTRY`/`PUBLISHER_REGISTRY`-as-a-config-string-resolver, which is a genuinely different problem than the CROSS-PACKAGE-BOUNDARY problem this note resolves; `PUBLISHER_REGISTRY` in 04-04 correctly stays a plain dict because `MergePublisher` is `dataplat`-native and has no cross-package issue at all).

**The resolved design:**
1. `csv_processor`'s `ingest`/`discover` commands live in a NEW module, `packages/csv-processor/src/csv_processor/cli.py` — NOT inside `dataplat/cli.py`. This module imports `from dataplat.cli import cli` (the shared `click.Group` object) and attaches `@cli.command()`-decorated functions to it. `csv_processor` importing `dataplat` is the ALREADY-ESTABLISHED, permitted direction.
2. `dataplat.cli.main()` (the `[project.scripts] dataplat = "dataplat.cli:main"` entry point, UNCHANGED from Phase 3) gains a small discovery step, BEFORE dispatching to `cli.main(...)`: iterate `importlib.metadata.entry_points(group="dataplat.plugins")` and call `.load()` on each — this triggers `csv_processor.cli`'s import (and therefore its `@cli.command()` decorators) via a STRING-based, runtime lookup that import-linter's static analysis cannot see and does not flag, because no `import csv_processor` token exists anywhere in `dataplat`'s source.
3. `packages/csv-processor/pyproject.toml` gains `[project.entry-points."dataplat.plugins"]` with `csv_processor = "csv_processor.cli"` — the standard-library-recognized declaration that makes step 2's lookup find this module.
4. Result: `docker run <image> dataplat discover --dataset customers` and `docker run <image> dataplat ingest --assignment <uri>` both work, `ENTRYPOINT ["dataplat"]` and `cmds=["dataplat"]` in the KPO code (already verified in a prior research pass) are UNCHANGED, and `make imports` stays green.

**A second, related correction:** ARCHITECTURE.md's own diagram (§6.2) shows `discover_files` as a lightweight in-process Airflow `@task`, calling `dataplat.discovery` directly. This is IMPOSSIBLE as drawn: `dataplat` is never installed into the Airflow image (STACK.md's own PITFALLS G5: "do NOT plan to install csv_processor into the Airflow image" — the Airflow image pins `psycopg2-binary==2.9.12`, incompatible with `dataplat`'s `psycopg[binary,pool]>=3.3.4`). This plan's `discover` is therefore a SECOND `KubernetesPodOperator` task (using the SAME `csv-processor` image `ingest` uses), not a plain `@task`. A later plan's DAG file reflects this; this plan's job is to make `dataplat discover --dataset <name>` a real, working CLI invocation the DAG can shell out to via KPO.

`discover`'s CLI shape: `dataplat discover --dataset customers` — loads `configs/defaults.yaml` + `configs/datasets/{dataset}.yaml` via `dataplat.config.loader.load_config` (needs `configs/` present in the image filesystem, at the SAME relative path the loader is called with — this is why the Dockerfile changes), syncs via `ConfigRegistry.sync(dataset_name, config)`, calls `dataplat.discovery.discover_files(...)`, writes a receipt-shaped XCom summary (`{"status": "SUCCEEDED", "units": [{"assignment_uri":..., "idempotency_key":..., "run_id":...}, ...], "file_count": N}`) to `/airflow/xcom/return.json`.

`ingest`'s CLI shape: `dataplat ingest --assignment <s3-uri-or-local-path>` — fetches and validates the `AssignmentDocument` via `objects.get_object(...)` + `AssignmentDocument.model_validate_json(...)`, resolves `DatasetConfig` via `ConfigRegistry.get_by_id(assignment.config_version_id)` (NOT from `configs/*.yaml` — `ingest` does not need `configs/` in its image at all, only `discover` does), constructs `CsvSource(bucket=..., key=<from assignment.file.object_uri>)`, assembles `PipelineContext(source=csv_source, ...)`, calls `dataplat.pipeline.run.run_ingest(ctx)`.

| Boundary | Description |

| `dataplat.cli.main()` → installed entry points | A malicious or misconfigured installed package declaring a `dataplat.plugins` entry point could inject arbitrary code at CLI startup |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-04-02 | Tampering, Elevation of Privilege | `ingest`'s assignment-document read | mitigate | `AssignmentDocument.model_validate_json` is called before any field is used to build an object-store key or a `CsvSource` — verified by the acceptance criteria's structural read order |
| T-04-04 | Information Disclosure | `_write_xcom`'s FAILED-path payload | mitigate | The synthesized failure `Receipt` carries only `status`/`run_id`, never a raw exception message or traceback; a fuller `error_type`/`error_message` is logged via the existing `DataPlatformError`/structlog redaction path, never placed in the XCom-visible receipt |
