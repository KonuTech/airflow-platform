<objective>
Wire business-key extraction into every place a `RejectedRecord` is created, so the `business_key` field this phase's 08-16 plan added to the model and the DB column actually gets populated at reject time — the "capture-at-reject-time" half of the VALID-08 gap-closure design (D-23/D-25, `08-CONTEXT.md`).

Four `StreamingStage` rule classes (`CompletenessRule`, `PatternRule`, `ValidityRangeRule`, `UniquenessRule`) each construct `RejectedRecord`s from an already-parsed row tuple whose column positions are reliable (they all run AFTER `RaggedRowGuard`, per `load/staging.py`'s `_build_stages` D-08 ordering) — each needs to know WHICH row index holds the dataset's business-key column (independent of which column that specific rule instance is itself checking) and extract it. `ReferentialIntegrityBarrier`'s orphan rows already select `order_id` in its anti-join SQL (`validate/referential.py`'s `_ANTI_JOIN_SQL`) — trivial to wire, no new query. `RaggedRowGuard` deliberately gets ZERO changes: D-25 requires a structurally-ragged row's business_key to stay `None` (unreliable column positions), and `RejectedRecord.business_key` already defaults to `None`, so simply never passing it there is correct and requires no code change.

Purpose: make `business_key` a real, populated value on every `RejectedRecord` this platform's real datasets (`customers`, `orders`) can produce, not just a schema column nothing ever fills in.
Output: `business_key_index` threading from `StagingLoader._build_stages`/`_build_quality_stages` into the four streaming rule classes, extraction logic in each, and `business_key=order_id` in `ReferentialIntegrityBarrier`.
</objective>
