<objective>
Make `orders` a second, fully-working dataset through the existing vertical-slice pipeline — not a config-only stub. This closes a real gap found while reading the codebase: `pipeline/run.py` and `load/publish/merge.py` are today hardcoded, single-dataset (`_CUSTOMERS_TARGET_COLUMNS`, `INSERT INTO normalized.customers` literally in SQL text). D-13/D-14 require `orders` to run through "the SAME config-driven Source→Stage→Publisher pipeline, no new capability invented" — this plan is the minimal, precedent-following generalization that makes that literally true, mirroring the codebase's own established "hardcoded per dataset, not yet a generic multi-dataset design" pattern (both module docstrings say so explicitly) rather than inventing a premature fully-generic publisher.

Purpose: every later plan in this phase that proves VALID-07 (referential integrity between `orders` and `customers`) depends on `orders` actually being able to publish rows for real. This plan is the prerequisite substrate.
Output: a dataset-keyed target-columns lookup in `run_ingest`, a new `OrdersMergePublisher`, a new `"merge_orders"` registry entry, `configs/datasets/orders.yaml` (D-13..D-17, no `quality:` block yet — that lands in plan 08-08), and an integration test proving a synthetic orders row publishes and re-publishes idempotently.
</objective>
