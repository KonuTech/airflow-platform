<objective>
Build the Airflow-side LOAD-10 file-integrity gate as a standalone, DAG-independent module covering every check LOAD-10 names against a real object: wrong extension, empty file, object instability between two HEAD calls (D-21), and unreadable/unhashable content (D-22's "checksum" -- there is no external checksum file to compare against, per D-22; "checksum" here means confirming the object is genuinely readable by computing its `content_sha256`). On any failure, the gate records the rejection as a NEW `meta.files` row (never a KPO pod launch, never a `dataplat` import -- D-18/D-20, ADR-0004 unchanged) because the code that normally creates a `meta.files` row (`discover_files`) never runs for a file this gate rejects. Because `meta.files.content_sha256` is `NOT NULL` and part of a `UNIQUE(dataset_id, object_uri, content_sha256)` constraint, this plan makes EVERY rejection path -- including the ones where no real file hash can ever be computed (wrong extension, an unstable object, an unreadable stream) -- write a real `meta.files` row anyway, by hashing a deterministic `REJECTED:<reason>` sentinel instead of the (unknowable) object content for those cases; the one genuinely knowable-content case (an empty file) gets the real SHA-256 of zero bytes, which needs no network read at all.

This plan also resolves the concrete mechanism by which an Airflow DAG learns WHICH keys to gate: `S3KeySensor` only returns a boolean from `poke()`/`execute()` -- it pushes no key list to XCom in the pinned `apache-airflow-providers-amazon` version (verified against the installed provider's `S3KeySensor.execute`/`poke` source: `execute()` returns `None`, `poke()` returns `bool`, no XCom push of matched keys exists). `list_matched_keys`, this plan's second building block, is the concrete, Airflow-native answer: a thin `@task` around `S3Hook.list_keys(..., apply_wildcard=True)`, listing the same `bucket`/`prefix` shape `wait_for_files`' own `bucket_key` already names, so plan 08-12 can `.expand(key=list_matched_keys(...))` over `integrity_gate` without inventing anything at DAG-authoring time.

Purpose: this is the "reject before any parsing occurs" gate ROADMAP's success criterion #4 names explicitly ("checksum mismatch, size mismatch, wrong extension, empty, or missing its `_BATCH_COMPLETE` marker"), and it is architecturally independent of every other stream in this phase (touches no `dataplat` code, no migration) -- it can and should land in Wave 1, wired into the two DAGs later (plan 08-12).
Output: `integrity_gate.py` (now exporting both `list_matched_keys` and `integrity_gate`), a `test_dag_thinness.py` exemption entry (matching `kpo.py`'s own precedent), and a full unit-test suite covering every check path plus the sentinel-hash rejection path, with `S3Hook`/`psycopg` fully mocked.
</objective>

Define `@task def integrity_gate(bucket: str, key: str, dataset_name: str) -> dict[str, object]`:
1. **Extension check**: if `not key.endswith(_EXPECTED_EXTENSIONS)`, call `_reject_file(bucket=bucket, key=key, dataset_name=dataset_name, reason=f"{key}: extension not in {_EXPECTED_EXTENSIONS}", content_sha256=None, size_bytes=None)` then `raise AirflowFailException(...)` -- no HEAD call needed first, the key alone answers this.
2. `hook = S3Hook(aws_conn_id="minio_default")`; `client = hook.get_conn()`; `first = client.head_object(Bucket=bucket, Key=key)`.
3. **Empty-file check**: if `first["ContentLength"] == 0`, reject with reason `f"{key}: empty file (0 bytes)"`, passing `content_sha256=hashlib.sha256(b"").digest()` explicitly (the real, exact hash of the object's known-empty content -- no GET needed, `b""` is authoritative here, not a sentinel) and `size_bytes=0`.
4. `time.sleep(_STABILITY_CHECK_INTERVAL_SECONDS)`; `second = client.head_object(Bucket=bucket, Key=key)`.
5. **Stability/size check (D-21)**: if `(first["ContentLength"], first["ETag"]) != (second["ContentLength"], second["ETag"])`, reject with reason `f"{key}: object not stable between HEAD checks"`, `content_sha256=None` (ambiguous which snapshot's bytes would even be hashed -- `_reject_file` resolves the sentinel), `size_bytes=first["ContentLength"]` (best-effort, non-authoritative but still informative).
6. **Checksum/readability check (D-22)**: attempt a real streaming read -- `body = client.get_object(Bucket=bucket, Key=key)["Body"]`, hash it in bounded chunks (mirror `discovery.py`'s own `_HASH_CHUNK_BYTES = 1_048_576` streaming-hash convention -- duplicate the constant and loop shape here, do not import `dataplat.discovery`) into `hashlib.sha256()`. On ANY exception during this read (a network error, a genuinely corrupted/unreadable object), reject with reason `f"{key}: object could not be read/hashed: {exc}"` and `content_sha256=None` (`_reject_file` resolves the sentinel), `size_bytes=second["ContentLength"]`. On success, keep the computed `content_sha256`/`content_sha256.hexdigest()`.
7. Every rejection path calls `_reject_file(...)` then raises `AirflowFailException` with the same message -- D-20: no `run_id`, no `meta.ingestion_runs` row, no `rejected_records` rows, a dead end before any pod launches.
8. On full success (all checks pass), return `{"content_length": second["ContentLength"], "etag": second["ETag"], "content_sha256_hex": digest.hexdigest()}` -- this gate does NOT itself write a `meta.files` row on success (that remains `discover_files`'s existing, unchanged job moments later in the DAG; writing here would race/duplicate that INSERT).

Define `_reject_file(*, bucket: str, key: str, dataset_name: str, reason: str, content_sha256: bytes | None, size_bytes: int | None) -> None`: resolves a DSN via Airflow's own `PostgresHook(postgres_conn_id="analytics_db_default").get_uri()` (or `BaseHook.get_connection(...).get_uri()` if `PostgresHook` is unavailable in the pinned `apache-airflow-providers-postgres` version -- verify before choosing), opens a short-lived `psycopg.connect(dsn)` (a real, explicit, narrow dependency of this one function). Resolve the ACTUAL `content_sha256` to write: when the caller already passed a real, known hash (the empty-file case), use it as-is; when the caller passed `None` (extension/instability/unreadable -- the real bytes are unknown or ambiguous), compute a deterministic sentinel instead: `resolved_hash = content_sha256 if content_sha256 is not None else hashlib.sha256(_REJECTION_SENTINEL_PREFIX + f"{bucket}/{key}:{reason}".encode("utf-8")).digest()` -- deterministic per `(object_uri, reason)` so a repeated identical failure on the same object (e.g. the sensor keeps re-matching a still-unstable file) idempotently `ON CONFLICT`s onto the SAME row instead of raising a duplicate-row error, while a DIFFERENT reason for the same object_uri is intentionally a distinct row (a real change in why the object was rejected). `_reject_file` therefore now ALWAYS has a non-null `content_sha256` to write and never skips the INSERT -- this is the concrete D-20 fix: every LOAD-10 rejection path, with no exceptions, produces a real `meta.files` row.

Inside one transaction: (a) resolve/create `dataset_id` via the EXACT upsert shape `get_or_create_dataset` uses (`INSERT INTO meta.datasets (dataset_name) VALUES (%s) ON CONFLICT (dataset_name) DO UPDATE SET dataset_name = EXCLUDED.dataset_name RETURNING dataset_id`, bind `dataset_name`) -- duplicated here as raw SQL, never imported from `dataplat` (ADR-0004); (b) `INSERT INTO meta.files (dataset_id, object_uri, content_sha256, hash_version, size_bytes, filename, status) VALUES (%s, %s, %s, 1, %s, %s, %s) ON CONFLICT (dataset_id, object_uri, content_sha256) DO UPDATE SET status = EXCLUDED.status RETURNING file_id`, binding `dataset_id, f"s3://{bucket}/{key}", resolved_hash, size_bytes or 0, key.rsplit("/", 1)[-1], f"REJECTED: {reason}"`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| S3/MinIO object metadata/content -> integrity_gate | `ContentLength`/`ETag`/object bytes are provider-controlled (MinIO), not directly attacker-influenceable in this platform's threat model, but the comparison/hashing logic must not be bypassable by a crafted response shape |
| integrity_gate -> meta.files | The one Airflow-scheduler-process write to the analytical DB in this entire codebase — a genuinely new architectural surface |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-04 | Tampering | `_reject_file`'s SQL construction (dataset upsert + files insert) | mitigate | Parameterized `%s` binding for every value — matches this codebase's `_PUBLISH_SQL`/`get_or_create_dataset` precedent; verified by Task 2's Test 6 |
| T-08-05 | Elevation of Privilege | integrity_gate's DSN resolution | mitigate | Uses the SAME Vault-backed Airflow Connection mechanism SEC-05 already proved (`AIRFLOW__SECRETS__BACKEND=VaultBackend`) — no new credential path, no literal DSN in code |
| T-08-06 | Denial of Service | Unbounded stability-check retries | accept | This gate runs exactly once per file per `wait_for_files` poke (no retry loop inside `integrity_gate` itself) — a persistently-unstable object simply fails discovery for that poke window and is re-evaluated on the next `S3KeySensor` cycle, never spins |
| T-08-24 | Denial of Service | Streaming the whole object into a SHA256 hash inside the Airflow worker process (not a bounded pod) | mitigate | Reads in bounded `_HASH_CHUNK_BYTES` chunks (mirrors `discovery.py`'s own streaming-hash discipline), never loads the whole object into memory at once |
| T-08-25 | Repudiation | A gate-failure `meta.files` row whose `content_sha256` is a sentinel, not the object's real bytes hash | accept | The row's `status` column carries the real, human-readable rejection reason (D-20's actual traceability requirement); the sentinel exists solely to satisfy the `NOT NULL`/`UNIQUE` constraint for a case where the real bytes are unknown or ambiguous by definition (wrong extension = never read; unstable object = which snapshot?) — documented in `_reject_file`'s own docstring, not a silently misleading value |
