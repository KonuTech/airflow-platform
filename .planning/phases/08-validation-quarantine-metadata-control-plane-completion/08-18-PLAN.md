Ordering is load-bearing (CR-01, existing comment above this block): resolve MUST run BEFORE
`record_rejected_records`, so a run's own just-created rejects are never visible to its own
resolve call. This plan's business-key-scoped replacement PRESERVES this exact ordering --
it is what makes CR-01's guarantee hold under the new predicate too (a run's own fresh reject's
business key was never published this run -- the row that got rejected never entered staging
in the first place -- so `SELECT DISTINCT` over the staging table can never surface it).

`staging_result.staging_table` (e.g. `"staging.customers__r8123"`) is still a live, queryable
table at this point in the transaction -- the `DROP TABLE` happens later, on a SEPARATE
connection, AFTER this whole transaction commits (`run_ingest`'s own code, confirmed by direct
read).

`_TARGET_COLUMNS_BY_DATASET`/`_target_columns_for_dataset` (same module, `pipeline/run.py`,
existing) is NOT needed here -- this plan queries the business-key COLUMN NAME (from
`ctx.config.columns[].business_key`), not its index.
