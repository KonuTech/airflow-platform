`airflow backfill create --dag-id <dag_id> --from-date <iso> --to-date <iso> --reprocess-behavior
completed --max-active-runs <N> [--dry-run]` (verified live against this cluster's installed
Airflow 3.3.0 this session) is the ONLY trigger mechanism (D-11). Both DAGs are `schedule="*/1 *
* * *"` — size the window in MINUTES, not years: `--dry-run` first to see the enumerated DagRun
count, then a small pilot (5-10 DagRuns) before committing to the window RESEARCH.md's own worked
estimate suggests (~20-30 minutes / 15+ ticks per dataset, to drain `discover_files`'s
`max_units_per_run: 100` cap across ~730 files/dataset at least twice — once to discover
everything, once for the idempotency re-run).

`tests/e2e/slice/test_backfill_reentry.py`'s CLI-invocation-via-`kubectl exec` pattern (line
~392-ish, grepped this session) and `Backfill.max_active_runs` (Airflow's own CLI flag, default 10,
verified via `airflow backfill create --help`) govern D-12's bounded parallelism — start with a
conservative `--max-active-runs 3`, falling back to `--max-active-runs 1` (sequential) if the live
cluster shows `FailedScheduling: Insufficient cpu` events during the pilot (this project's own
documented, recurring CPU-starvation failure mode, STATE.md).

`meta.v_run_recovery` (plan 09-06), `meta.watermarks`/`meta.watermark_history` (plan 09-02),
`meta.reconciliation_results` (plans 09-02/09-07/09-08), `meta.processing_gaps` (plan 09-10) are
the SQL surfaces this test's assertions query against — no new query surface needed, everything
already exists.
