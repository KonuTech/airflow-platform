<interfaces>
`list_matched_keys(bucket: str, prefix: str)` (`airflow/dags/_common/integrity_gate.py`, already
imported into both DAGs) returns the real key list for THIS DagRun's S3 listing — its return value
is what `gate = integrity_gate.override(...).partial(...).expand(key=matched_keys)` fans out over
today. This plan inserts a new task reading that SAME return value, without changing
`list_matched_keys` itself.

`dag_run.backfill_id` (Airflow 3.3.0's `DagRun` model, verified via RESEARCH.md's direct
`scheduler_job_runner.py` read this session) is `NULL` for a live scheduled run and set for every
backfill-triggered `DagRun` — a gap record is only meaningful for a backfill run (a live run
finding zero new files every minute is the ordinary, expected steady state, not a gap); gate the
new task on `dag_run.backfill_id is not None`.

`airflow/dags/_common/run_stage_recorder.py` (plan 09-04) and `airflow/dags/_common/integrity_gate.py`
`_reject_file` are this plan's exact ADR-0004-exception templates — `gap_recorder.py` is the
FOURTH such module (after `integrity_gate.py`, `kpo.py`/`tracing_kpo.py`, and
`run_stage_recorder.py`); cite the count in its own docstring.

`tests/e2e/slice/test_pod_kill_retry.py::test_pod_kill_mid_load_produces_no_duplicates` (verified
this session, full read) is the exact live-kill pattern: poll a mid-flight signal, `kubectl -n etl
delete pod <pod_name> --wait=false`, poll for the retried pod reaching a terminal SUCCEEDED state,
assert exact row counts. `dbt_build` has no `rows_read`-style heartbeat (it is opaque to
`meta.ingestion_runs`) — the mid-flight signal is plan 09-09's own `mark_dbt_build_running` write:
`meta.run_stages WHERE stage_name='DBT_BUILD' AND status='RUNNING'`. The real pod to kill is found
via Airflow's own `kubectl get pods -l dag_id=<dag>,task_id=dbt_build -n etl` label selector
(Airflow's KPO auto-labels every launched pod with `dag_id`/`task_id`/`try_number`) — this plan does
NOT need `meta.run_stages.pod_name` populated to find the pod.
</interfaces>
