<objective>
Build the third sanctioned ADR-0004 exception (alongside `integrity_gate.py` and
`kpo.py`/`tracing_kpo.py`): a small, `dataplat`-free module the DAGs use to record a `DBT_BUILD`
`meta.run_stages` row directly via plain `psycopg`, since `dbt_app` has zero grant on
`meta.run_stages` (migration 0025's deliberate D-02 decoupling) and dbt's own idempotency must stay
fully decoupled from the Python claim/lease/heartbeat mechanism (D-14).

Purpose: This closes the one blind spot in the current recovery-visibility design — today
`meta.run_stages` only tracks `STAGE_LOAD`/`PUBLISH`, so a single query cannot answer "what
succeeded, what remains" for the WHOLE pipeline (LOAD-06). This plan builds the recording
mechanism only; DAG wiring (calling these tasks from `csv_ingest_customers`/`csv_ingest_orders`)
is plan 09-09, once this module and the `meta.v_run_recovery` view (plan 09-06) both exist.
Output: `airflow/dags/_common/run_stage_recorder.py`, unit-tested standalone (no live DAG needed
yet).
</objective>

<interfaces>
`airflow/dags/_common/integrity_gate.py`'s `_reject_file` (lines ~206-277, verified this session) is
the exact ADR-0004-exception template: a plain-`psycopg`, `BaseHook.get_connection(...).get_uri()`
DSN resolution, no `dataplat` import anywhere in the module. Its own module docstring's "a second,
narrowly-scoped exception... alongside `kpo.py`/`tracing_kpo.py`" framing is the precedent to extend
— this module is the THIRD.

`meta.run_stages` (migration 0025, `stage_name` is plain `Text`, `UNIQUE(run_id, stage_name)`) needs
NO schema change for a `'DBT_BUILD'` value — it is app-validated vocabulary, not a native ENUM (the
migration's own documented design note).

`claim_run_stage`/`complete_run_stage`'s exact SQL shapes (`packages/dataplat/src/dataplat/metadata/postgres.py`,
lines ~458-556, verified this session) are the shapes to DUPLICATE as raw SQL here — never
imported. Unlike `STAGE_LOAD`/`PUBLISH` (each claimed by exactly one pod per `run_id`), `dbt_build`
is a SINGLE KPO task per DagRun that processes potentially MANY staged `run_id`s in one `dbt build`
invocation — so this module's write happens ONCE PER `run_id` currently eligible (STAGE_LOAD
SUCCEEDED, no DBT_BUILD row yet or a retryable one), not once per pod.

`meta.ingestion_runs` — a run is eligible for `dbt_build` once its `STAGE_LOAD` `run_stages` row is
`'SUCCEEDED'`. The query: `SELECT r.run_id FROM meta.ingestion_runs r JOIN meta.run_stages sl ON
sl.run_id = r.run_id AND sl.stage_name = 'STAGE_LOAD' AND sl.status = 'SUCCEEDED' LEFT JOIN
meta.run_stages db ON db.run_id = r.run_id AND db.stage_name = 'DBT_BUILD' WHERE db.run_id IS NULL
OR db.status IN ('FAILED', 'RUNNING')` — this last `RUNNING` branch intentionally re-includes a
run whose previous `dbt_build` attempt never reached a terminal status (Airflow's own task retry,
not a lease-expiry timer, is what re-drives this — see this plan's Task 2 note on D-17).
</interfaces>
