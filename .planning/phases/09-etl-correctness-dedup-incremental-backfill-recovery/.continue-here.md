# BLOCKING CONSTRAINTS — Read Before Anything Else

> These are not suggestions. Each constraint below was discovered through failure.
> Acknowledge each one explicitly before proceeding.

- [ ] CONSTRAINT: Host-disk-vs-Docker-internal-disk confusion — Docker Desktop's `docker_data.vhdx` is a dynamically-expanding virtual disk that grows the Windows `C:` drive usage but never shrinks it back, even after `docker system prune`, `docker volume rm`, or per-node containerd image pruning. During this session, `C:` dropped to 343MB free and the Docker daemon actually crashed from host disk exhaustion mid-execution. Removing ~45GB of genuine waste from inside Docker (an unrelated project, stale build tags, unused build cache) reclaimed **zero** bytes of host `C:` space — confirmed by direct measurement before and after. Structural mitigation: before dispatching Wave 6 (09-11, the heaviest remaining plan — live 2-year corpus, concurrent DagRuns, real MinIO uploads), run `df -h /mnt/c` (or check actual Windows drive free space) and confirm several GB+ free. Do NOT trust `docker system df` as a proxy for host disk headroom — it only reports Docker-internal logical usage. If `C:` is still critically low, the only real fix is a host-side VHDX compact: `wsl --shutdown` then `Optimize-VHD -Path "$env:LOCALAPPDATA\Docker\wsl\disk\docker_data.vhdx" -Mode Full` (or `diskpart` → `select vdisk file="..."` → `compact vdisk`) from an admin Windows PowerShell.

**Do not proceed until this box is checked.**

| Docker-internal cleanup mistaken for host-disk relief | `docker image prune`/`volume rm`/`builder prune`/per-node `crictl rmi` all free space *inside* the vhdx, not on the host `C:` drive. Spent significant effort this session on internal cleanup before realizing it wasn't moving the host-disk number at all. | blocking | Always check `df -h /mnt/c` (host reality) separately from `docker system df` (Docker's internal view) before deciding cleanup is "done." Only a VHDX compact from Windows moves the host number. |
