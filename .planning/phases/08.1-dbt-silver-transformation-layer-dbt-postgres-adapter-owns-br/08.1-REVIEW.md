# Phase 08.1: Code Review Report

**Reviewed:** 2026-08-19T10:18:51Z
**Depth:** standard

## Summary

This phase adds a dbt-owned bronze-to-silver transformation layer (dbt project,
`silver.customers`/`silver.orders`, the `meta.dedup_audit`/`meta.dedup_decisions`
audit trail, `meta.run_stages`, the `dbt` ServiceAccount/Vault role, and the
`discover -> stage -> dbt_build -> publish` DAG split) on top of an already very
mature, heavily-documented codebase. The engineering discipline is unusually
high: SQL identifiers are never string-interpolated from row content, RBAC/Vault
boundaries are proven by dedicated tests, and three of the ten new migrations
(0028/0029/0030) are themselves honest, well-documented fixes for gaps the
authors found via live E2E testing rather than in code review — a genuinely
good sign about how this team responds to defects.

That said, one real, reachable correctness bug survived into `dbt/models/silver/
silver_orders.sql`: the incremental model's business-key tie-break `ORDER BY
order_date DESC` relies on PostgreSQL's default NULL ordering, which sorts NULLs
*first* in a `DESC` ordering — the exact opposite of what the model's own
"latest wins" design intends. `orders.order_date` is legitimately nullable per
`configs/datasets/orders.yaml`, so this is not a hypothetical: a bronze order row
with a missing `order_date` will silently outrank a bronze row for the same
`order_id` that has a real, later date, and will keep winning the dedup contest
on every subsequent incremental run. No test in this phase exercises a NULL
`order_date`/`event_ts` bronze row, so this gap is untested as well as unfixed.

The remaining findings are lower-severity: the same NULL-ordering pattern exists
(currently unreachable, but unguarded) in `silver_customers.sql`; the dedup
tie-break's final key (`_source_row_number`) is not globally unique across files,
leaving a narrow non-determinism window; and a few smaller quality/documentation
notes.

## Critical Issues

### CR-01: `silver_orders.sql`'s dedup tie-break ranks a NULL `order_date` as the winner

**File:** `dbt/models/silver/silver_orders.sql:94`
**Issue:**

```sql
business_key_ranked as (
    select
        *,
        row_number() over (
            partition by order_id
            order by order_date::date desc, _source_row_number desc
        ) as rn
    from all_contenders
)
```

PostgreSQL's documented default NULL ordering is: `NULLS LAST` for `ASC`,
`NULLS FIRST` for `DESC` (unless overridden with an explicit `NULLS FIRST` /
`NULLS LAST` clause). This `ORDER BY ... DESC` never overrides that default, so
a bronze row whose `order_date` is `NULL` sorts *ahead of* every row with a real,
later `order_date` within the same `order_id` partition — it wins `rn = 1` and
becomes the silver (and eventually gold, via `merge_orders.py`) row of record,
even though it is objectively not the "latest" version of that order.

This is reachable, not merely theoretical: `configs/datasets/orders.yaml`
declares `order_date: {type: date, nullable: true, required: true}`, and
`migrations/versions/0022_staging_customers_orders_durable_tables.py` declares
`staging.orders.order_date` as `nullable=True` — a NULL `order_date` is a
legitimate, validated business state for this dataset (an order recorded before
its date was known, for example), not a data-quality violation the pipeline
rejects upstream. `merge_orders.py`'s own module docstring (`WR-04`) already
demonstrates the authors were aware `order_date` can be NULL and specifically
guarded the gold-layer `ON CONFLICT ... WHERE` clause for it — but that
awareness did not carry over to this new dbt ranking logic.

Once a NULL-`order_date` row wins in silver, it keeps winning on every future
`dbt build`: `delete+insert` re-selects the same wrong winner from
`all_contenders` (new bronze ∪ the currently-resident silver row) every time,
so a later file that legitimately supplies the missing/corrected date for that
`order_id` will still lose the tie-break to the NULL row, silently.
`meta.dedup_audit`/`meta.dedup_decisions` will faithfully record this as a
"correct" dedup decision, with no error and no visible symptom other than wrong
data in `normalized.orders`.

No test in this phase (`test_dbt_silver_dedup.py`, `test_dbt_silver_incremental.py`)
seeds a NULL `order_date` bronze row, so this gap is currently unguarded by CI.

**Fix:**

```sql
order by order_date::date desc nulls last, _source_row_number desc
```

Add an integration test seeding one bronze row with `order_date = NULL` and a
sibling row with a real `order_date` for the same `order_id`, asserting the
dated row wins.

## Warnings

### WR-01: `silver_customers.sql` has the same unguarded NULL-ordering pattern (latent)

**File:** `dbt/models/silver/silver_customers.sql:130`
**Issue:**

```sql
order by event_ts::timestamptz desc, _source_row_number desc
```

`event_ts` currently cannot be NULL under `configs/datasets/customers.yaml`
(`nullable: false`), so CR-01's failure mode is not reachable today for
`customers` through the normal validated ingest path. However:
`migrations/versions/0022_staging_customers_orders_durable_tables.py` still
declares `staging.customers.event_ts`/`silver.customers.event_ts` as
`nullable=True` at the database level, and nothing in this SQL defends against
a NULL reaching it (e.g. a future relaxation of the column contract, a
hand-seeded backfill row, or a bug elsewhere in the pipeline that lets a NULL
slip past validation). Given CR-01 shows this exact pattern is a live bug
elsewhere in the same file pair, this should be fixed defensively at the same
time, not left as a second latent instance of the identical defect.

**Fix:** `order by event_ts::timestamptz desc nulls last, _source_row_number desc`

### WR-02: Dedup tie-break's final key is not globally unique, leaving a narrow non-determinism window

**File:** `dbt/models/silver/silver_customers.sql:128-131`, `dbt/models/silver/silver_orders.sql:92-95`
**Issue:** The `row_number() over (partition by <business_key> order by <event_ts|order_date> desc, _source_row_number desc)` tie-break's final key, `_source_row_number`, is only unique *within one file* (`StagingLoader.load()` resets `next_source_row_number` to `1` per staging attempt). Two bronze rows for the same business key, contributed by two *different* files/batches, can share both an identical `event_ts`/`order_date` and an identical `_source_row_number` (e.g. both are each file's first data row). PostgreSQL's `row_number()` gives no further deterministic tiebreak in that case — which of the two tied rows receives `rn = 1` depends on physical row order, which is not guaranteed stable across two `dbt build` invocations over the same underlying data. This is a narrow but real violation of this project's own explicitly-stated determinism constraint (CLAUDE.md: "Same source data + configuration + processor version yields the same logical result... unavoidable non-determinism must be documented"). The identical weakness already exists in `merge.py`/`merge_orders.py`'s own `DISTINCT ON` ordering (pre-existing, not introduced by this phase), but this phase makes it the *sole* dedup mechanism for silver, with no downstream guard equivalent to the gold-layer `event_ts >=` check.

**Fix:** Add a genuinely unique final tiebreak, e.g. `_file_id desc` (or `_run_id desc, _file_id desc`), after `_source_row_number desc`, in both models' `business_key_ranked` window function.

### WR-03: `tests/integration/conftest.py`'s `run_dbt_build` fixture never exercises the real `dbt_app` role

**File:** `tests/integration/conftest.py:279-302`
**Issue:** `_dsn_to_dbt_env_vars` is built from `migrated_dsn`, which is the testcontainers *superuser* DSN — every `dbt`-marked integration test (`test_dbt_silver_dedup.py`, `test_dbt_silver_incremental.py`, `test_dbt_dedup_audit.py`) therefore runs `dbt build` as the database superuser, never as the least-privilege `dbt_app` role migration 0021/0028/0029 carefully scope. This means none of this phase's "real `dbt build`" integration tests actually prove `dbt_app`'s grants are sufficient for a real build to succeed — that gap is only closed by `test_migrations.py`'s static grant assertions (which never run a real build under the role) and by the live-cluster E2E suite (`test_dbt_silver_pipeline.py`, one dataset, one happy path). This is already partially self-documented (migration 0028's docstring explicitly calls out the same class of gap for `meta.datasets`), but it remains a real, un-remediated test-design gap for this fixture specifically.

**Fix:** Consider adding one `dbt`-marked test that runs `dbt build` with `DBT_PG_USER=dbt_app` (setting a password via `ALTER ROLE dbt_app WITH PASSWORD` on the testcontainers instance first) to prove the grants are sufficient end-to-end without depending on a live cluster.

## Info

### IN-01: `_dbt_loaded_at` is refreshed even when the winning row's content is unchanged

**File:** `dbt/models/silver/silver_customers.sql:139`, `dbt/models/silver/silver_orders.sql:103`
**Issue:** `delete+insert` re-inserts every `rn = 1` row on every run, including rows where the winner is the pre-existing silver row itself (no new bronze data actually changed anything for that business key) — `now() as _dbt_loaded_at` therefore advances even though nothing about the row's content changed. Anyone relying on `meta.v_customers_lineage.silver_loaded_at` to answer "when did this row's data last change" will get "when did dbt last touch this row" instead, which is a subtly different and less useful signal.
**Fix:** Either document this explicitly in the model's header comment (it currently documents *why* `_dbt_loaded_at` is dbt-populated, but not this staleness nuance), or preserve the winner's own prior `_dbt_loaded_at` when the winning contender came from `existing_silver_contenders` rather than `new_bronze`.

### IN-02: `resolve_window`/`build_stage_args`/`aggregate_receipts` are duplicated verbatim across both DAG files

**File:** `airflow/dags/csv_ingest_customers.py:45-71`, `airflow/dags/csv_ingest_orders.py:46-72`
**Issue:** These three `@task` functions are byte-for-byte identical (modulo the log message's dataset name) between the two DAG files. This predates this phase (the pattern was already established for `csv_ingest_customers.py`/`csv_ingest_orders.py`), and the codebase's own stated convention is that `_common/` is for KPO-builder helpers only, "NEVER business logic" — but these three functions are pure orchestration glue, not business logic, so extracting them to a shared `_common` module would not violate that rule and would remove duplicate maintenance surface (e.g. a future bug fix in `build_stage_args` would need to be applied in two places).
**Fix:** Not required for this phase, but worth tracking as a follow-up: factor `resolve_window`/`build_stage_args`/`aggregate_receipts` into `_common/` with a `dag_id`-derived log prefix.

### IN-03: `kpo.py`'s `on_finish_action="delete_pod"` deletes `dbt_build` pods immediately even on failure

**File:** `airflow/dags/_common/kpo.py:132-163`
**Issue:** This is a deliberate, well-documented tradeoff for the `discover`/`stage`/`publish` pods (see the inline comment describing a real production incident it fixes), but it now also applies unconditionally to `dbt_build`, whose failures are a genuinely new failure class this phase introduces (a real `dbt run`/`dbt test` failure, contract violation, or `dedup_audit_post_hook` SQL error). `get_logs=True` captures container stdout/stderr before deletion, which covers most debugging needs, but a `dbt build` failure that leaves useful state behind (e.g. a partially-materialized table before a contract check fails) has no forensic pod to inspect afterward, unlike the documented "keep failed pods" alternative that was explicitly rejected for the CPU-leak reason described in the comment.
**Fix:** No action required — flagging only so a future incident involving an undiagnosable `dbt_build` failure has this tradeoff on record as a candidate cause, not a new bug.
