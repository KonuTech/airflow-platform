## Decisions Made

- **Did not bump `_PIPELINE_VERSION`** to manufacture Task 3 backfill evidence, even though it would have been the fastest path. That constant's own code comment documents it as "the only sanctioned way to signal a change to the PIPELINE SHAPE" — no genuine pipeline-shape change happened in this session, so bumping it would have written a false, permanent marker into the live database's lineage history, directly conflicting with this project's own Core Value (traceable, trustworthy lineage). Flagged this to the orchestrator before proceeding rather than deciding unilaterally.
- **Regenerated exact historical fixture bytes instead.** `tests/e2e/slice/test_backfill_reentry.py`'s `_build_customers_csv(base_customer_id, bad_row_name)` has no randomness in its row *content* — only `base_customer_id` varies per run, and that value is recoverable from the 3 already-published `normalized.customers` rows for each historical file_id (they are literally `base_customer_id`, `base_customer_id+1`, `base_customer_id+2`). Recovered it for 7 file_ids, regenerated, and verified `sha256` matched `meta.files.content_sha256` exactly for all 7 (270 bytes, byte-for-byte) — genuine, unfabricated historical content, not an approximation.
- **Re-uploaded to the files' ORIGINAL S3 keys, not new ones.** `discover_files`' `create_file` upsert recognizes a re-upload to the same `(dataset_id, object_uri, content_sha256)` as a rediscovery of the *same* `file_id`, which is what makes D-18's replay path (`find_latest_succeeded_run_for_file` + `replay_of_run_id`) fire. A new key would instead have hit the D-13 content-duplicate-skip path and created no run at all.
- **Used a single narrow backfill window (not a multi-day range).** `discover_files` re-lists the entire bucket on every call regardless of the triggering DagRun's own `logical_date`/window — this DAG's 1-minute schedule means a wide date range (as the plan's literal text implies) would create thousands of pointless DagRuns for zero additional discovery benefit. One backfill DagRun is sufficient to trigger the same full-bucket discover pass.
- **Used `airflow backfill create`, not `airflow dags backfill`.** The plan's literal CLI text is stale: Airflow 3.3.0 removed `dags backfill` entirely. Used the corrected, already-live-confirmed CLI shape `tests/e2e/slice/test_backfill_reentry.py`'s own docstring documents (`airflow backfill create --dag-id ... --from-date ... --to-date ... --reprocess-behavior completed`).

## Issues Encountered

**D-16's full historical parity is not achievable on this dev cluster, and this is an honest, confirmed limitation, not a bug.** `normalized.customers` carries 12,000,273 rows traced back to 31 historical file_ids from earlier in this phase's own development. 24 of those 31 are ~1M-row "large" fixture uploads whose `customer_id` values were shifted by a `random.SystemRandom()` offset at upload time that was never persisted anywhere — their raw content is permanently unreproducible. Their underlying S3 objects were also deleted by each e2e test suite's own (correct, by convention) cleanup. Only the 7 small, deterministic `test_backfill_reentry.py`-shaped fixtures (3 gold rows each) were genuinely recoverable, and 3 of those 7 were backfilled as a representative, honest proof of the D-18 replay mechanism — silver will never reach parity with gold's full 12M-row history on this cluster. This is a test-data-hygiene fact about this particular dev cluster's iterative testing history, not a platform defect: the mechanism itself (content-hash matching, `replay_of_run_id` lineage, re-claim under a new pipeline shape) is proven correct wherever genuine content is available, live and via `tests/integration/test_backfill_idempotency.py`'s own testcontainers-level proof.
