# Phase 08.1 Plan 08: dbt Silver Incremental Models Summary

**Two dbt-postgres incremental models (silver_customers/silver_orders) implementing business-key + exact-row-hash deduplication with a self-auditing post-hook, proven correct across three consecutive `dbt build` invocations (initial load, incremental delta with a late-arriving loser, no-op rebuild) against a real Postgres 18 database.**

## Performance

- **Duration:** ~90 min
- **Tasks:** 3
- **Files modified:** 16 (13 created, 3 modified)

## Accomplishments

- The full `dbt/` project scaffolding (project config, env-var-only connection profile, schema-name guard preventing `silver_silver`, bronze source declarations)
- `silver_customers`/`silver_orders`: `is_incremental()` + `_run_id`-keyed watermark filter (never `event_ts`, D-06), `row_number()`-based business-key ranking extended to compare new bronze rows against the currently-resident silver row for the same key (the mechanism that makes a late-arriving, business-stale row correctly lose instead of clobbering a correct existing row), `delete+insert` strategy (never `merge`, avoiding PG BUG #18279 the same way `MergePublisher` already does at gold), native `contract: enforced: true` validating against the Alembic-owned target tables
- `dedup_audit_post_hook`: one atomic `meta.dedup_audit` + `meta.dedup_decisions` write per invocation, in the SAME transaction as the model's own DML, classifying every dropped bronze row against the closed five-value reason vocabulary by comparing it directly to what the model's own materialization actually decided
- Four integration test files (7 test functions), all green against a real `dbt build`, proving DEDUP-01 through DEDUP-04, INCR-03/04, QUAL-10 and D-14's real DB constraint

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `dedup_audit_post_hook`'s `watermark_floor`/`source_relation`/`target_relation` design replaced after empirical failures**
- **Found during:** Task 2/3, live verification against a real Postgres + `dbt build` (manual pre-commit verification, not left to Task 3's own tests to discover)
- **Issue:** Three separate, real dbt Jinja/config-pass bugs, each verified with a real second `dbt build` invocation: (a) `source('bronze', ...)`/`this` Relation objects passed as macro arguments inside a `post_hook` capture resolved to the WRONG relation (the model's own default name) inconsistently across otherwise-identical runs; (b) a `run_query()`-computed `{% set %}` value captured into a `post_hook` string was frozen at an empty/zero value, because dbt evaluates `post_hook` config values as part of a separate, EARLIER "config extraction" pass where `run_query()` is unreliable — the model's OWN body (rendered in the later "real" compile pass) got the correct value, but the post-hook's captured copy did not; (c) `on_schema_change='fail'` (the plan's literal instruction) unconditionally failed every build, since the pre-existing Alembic-created target table carries `id`/`_ingested_at` columns the model's SELECT correctly never supplies.
- **Fix:** `source_schema`/`source_identifier`/`target_schema`/`target_identifier` are now plain strings, never Relation objects. The macro self-derives its own watermark from `coalesce(max(max_run_id), 0) from meta.dedup_audit where model_name = ...` instead of receiving one. `on_schema_change` changed to `'append_new_columns'`.
- **Files modified:** `dbt/macros/dedup_audit_post_hook.sql`, `dbt/models/silver/silver_customers.sql`, `dbt/models/silver/silver_orders.sql`
- **Verification:** Three consecutive `dbt build` invocations against a real Postgres 18 container (initial load, incremental delta including a late-arriving loser, no-op rebuild) all produced correct silver content and accurate `meta.dedup_audit` counts at every step; codified permanently by `test_dbt_silver_incremental.py`.
- **Committed in:** `9b5407b` (Task 2 commit)

**2. [Rule 1 - Bug] `alias='customers'`/`alias='orders'` added to both models**
- **Found during:** Task 2, same live verification session
- **Issue:** dbt's default relation naming derives the target table name from the model's own FILE name (`silver_customers.sql` → `silver.silver_customers`), not from the pre-existing Alembic-created table (`silver.customers`, migration 0023) the plan's own objective requires targeting. Without an explicit `alias`, `dbt build` silently created a second, wrong, empty table and never wrote to the real one.
- **Fix:** Added `alias='customers'`/`alias='orders'` to each model's `config()`.
- **Files modified:** `dbt/models/silver/silver_customers.sql`, `dbt/models/silver/silver_orders.sql`
- **Verification:** `\dt silver.*` after a build shows only `silver.customers`/`silver.orders`, matching migration 0023's tables; row content verified correct.
- **Committed in:** `9b5407b` (Task 2 commit)

**3. [Rule 2 - Missing critical functionality] `existing_silver_contenders` CTE added to both models' ranking**
- **Found during:** Task 2, designing for the plan's own D-06 must-have ("a late-arriving row... correctly loses... against an already-silver-resident row with a LATER event_ts, never overwriting it")
- **Issue:** RESEARCH.md's own Pattern 1 example ranks ONLY within the current incremental batch (new bronze rows since the last watermark). Under `delete+insert`, that ranking's output UNCONDITIONALLY replaces the existing silver row for any business key present in it — so a late-arriving, business-stale bronze row (the only contender for its key within the new batch) would win its own batch's ranking and silently clobber a correct, later, already-resident silver row. This is a genuine correctness gap in the plan's own cited interface, not something the plan's action text or RESEARCH.md flagged as needing this specific fix.
- **Fix:** Both models' ranking now includes an `existing_silver_contenders` CTE (the currently-resident target row for any business key with a new bronze contender this run), unioned into the SAME `row_number()` ranking pool as the new bronze rows, so the true latest-`event_ts`/`order_date` row always wins regardless of which "side" it came from.
- **Files modified:** `dbt/models/silver/silver_customers.sql`, `dbt/models/silver/silver_orders.sql`
- **Verification:** Live-verified: a late-arriving `customer_id` row with an older `event_ts` but a new `_run_id` was correctly excluded from silver, leaving the earlier-arrived, later-`event_ts` row untouched. Codified permanently by `test_dbt_silver_incremental.py`'s own core assertion.
- **Committed in:** `9b5407b` (Task 2 commit)

**4. [Rule 2 - Missing critical functionality] `dedup_audit_post_hook`'s dataset_id/`_ingested_at`/idempotency-key test fixture collisions fixed across all four test files**
- **Found during:** Task 3, running the full test suite together for the first time
- **Issue:** (a) `meta.config_versions` has a partial UNIQUE index allowing only one "current" row per dataset — since `migrated_dsn` is session-scoped and shared across all four test files, a second test seeding the SAME dataset ("customers"/"orders") without checking for an existing current config version collided. (b) Two different test functions within the SAME file both seeding with the identical `key_suffix` produced colliding `idempotency_key` values (`meta.ingestion_runs.idempotency_key` is globally unique, not per-dataset).
- **Fix:** Every per-file seed helper now reuses an existing `valid_to IS NULL` config version instead of always inserting; every seed call site uses a distinct `key_suffix` per dataset/test.
- **Files modified:** `tests/integration/test_dbt_silver_dedup.py`, `test_dbt_silver_incremental.py`, `test_dbt_dedup_audit.py`, `test_silver_constraints.py`
- **Verification:** All 7 tests pass together, in the same session, in a single `pytest` invocation.
- **Committed in:** `3576ab6` (Task 3 commit)

## Known Gaps (documented, not fixed by this plan)

- **`dbt_app` lacks `SELECT` on `meta.datasets`.** `dedup_audit_post_hook` resolves `dataset_id` via a scalar subquery against `meta.datasets` at hook-execution time. Migration 0024 (plan 08.1-05, already committed) granted `dbt_app` `USAGE` on schema `meta` and `SELECT, INSERT` on `meta.dedup_audit`/`meta.dedup_decisions` specifically, but no `SELECT` on `meta.datasets` itself. A live `dbt build` running as `dbt_app` (the real deployment's role, per Vault-resolved credentials) will fail this subquery with a permission error until a follow-up migration adds `GRANT SELECT ON meta.datasets TO dbt_app`. This plan's own integration tests run `dbt build` against the testcontainers superuser DSN, not `dbt_app`, so they do not exercise this gap — it is out of this plan's declared file scope (dbt project only, no new migrations) and is flagged here for a later plan (likely 08.1-09 or wherever the DAG orchestration/live deployment wiring lands) to close before a real `dbt_app`-authenticated build is attempted.

Extensive live empirical debugging was required to reach a working design — see "Deviations from Plan" above for the full technical account.
