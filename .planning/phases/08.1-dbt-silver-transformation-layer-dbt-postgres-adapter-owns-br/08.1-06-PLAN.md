<objective>
Give bronze staging a durable second home (D-01) and make the publish layer's contract honestly
named for what it now reads from.

**Two narrowly-scoped changes, no logic redesign:**
1. `StagingLoader` gains a new method, `promote_to_durable_bronze()`, that appends everything just
   staged into the scratch UNLOGGED buffer into the new durable, cumulative `staging.<dataset>`
   table (migration 0022, plan 08.1-01), then drops the scratch buffer — collapsing the whole
   scratch-buffer lifecycle (create → COPY → append → drop) into one connection's transaction
   scope, which is *simpler* than today's design (today the scratch buffer must survive past
   `StagingLoader.load()`'s own return, into a *later*, separate publish transaction; after this
   plan, nothing outside `stage_ingest` ever needs to see the scratch buffer again).
2. `Publisher.publish()`'s `staging_table` parameter is renamed `source_table` across the
   protocol and both concrete implementations (`MergePublisher`, `OrdersMergePublisher`) — a pure
   rename, not a logic change. `_PUBLISH_SQL`'s `FROM {staging_table}` interpolation already
   accepts *any* fully-qualified table name; from plan 08.1-10 onward the caller passes
   `silver.customers`/`silver.orders`, never a scratch table, so the parameter's old name would
   actively mislead a future reader.

Purpose: this is the physical-schema half of D-01 (Python side) and the naming-honesty half of
D-11 ("gold's publish SELECT should barely change — same columns, new FROM target"). Plan
08.1-10 (`pipeline/run.py`'s split) is where `stage_ingest`/`publish_ingest` actually call these —
this plan only builds and proves the two pieces in isolation.
Output: `StagingLoader.promote_to_durable_bronze()`, the `source_table` rename, and two test
files/extensions.
</objective>
