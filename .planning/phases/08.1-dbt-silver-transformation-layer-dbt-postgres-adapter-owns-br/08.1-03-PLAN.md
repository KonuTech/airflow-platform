Give dbt its own least-privilege Vault identity, mirroring `csv-processor`'s existing pattern
exactly: a new `dbt` Kubernetes ServiceAccount in namespace `etl`, a new Vault Kubernetes-auth
role/policy scoped to exactly one KV path (`etl/dbt-db`), and that path's five-field Postgres
credential (host/port/user/password/dbname — dbt-postgres needs discrete fields, not one DSN
string), with the password generated and set the same `kubectl exec ... ALTER ROLE` way
`etl_app`'s already is.

(dbt's own DB role) — without it, `docker/dbt/resolve_secrets.py` (plan 08.1-02) has no live
secret to resolve, and dbt_app (plan 08.1-01) has no way to authenticate as itself.
Output: `scripts/vault-bootstrap.py` extended with a `dbt` policy/role/secret block plus a unit
test proving it, and `kubernetes/rbac-etl.yaml` extended with a `dbt` ServiceAccount.
