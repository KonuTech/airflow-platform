**dbt gets its own least-privilege Vault Kubernetes-auth identity (ServiceAccount, policy, role) plus a live `etl/dbt-db` secret holding five discrete PostgreSQL connection fields, mirroring csv-processor's existing pattern exactly.**

## Accomplishments
- New `dbt` ServiceAccount in namespace `etl`, requiring zero new Role/RoleBinding since `etl-pod-launcher-role` already covers any ServiceAccount in `etl`
- New `_DBT_POLICY` (scoped to exactly `path "etl/data/dbt-db"`) and `_ensure_dbt_secret` in `scripts/vault-bootstrap.py`, wired into `bootstrap()` right after the existing csv-processor policy/role block
- `etl/dbt-db` deliberately writes five discrete credential fields (`host`/`port`/`user`/`password`/`dbname`), diverging from `_ensure_etl_secrets`'s single-`dsn`-field convention, since `docker/dbt/resolve_secrets.py` (plan 08.1-02) reads these five field names literally
- Two new offline unit tests proving `_ensure_dbt_secret`'s absent/present branches, both fully mocked (no live cluster, no kubectl, no network)

## Decisions Made
- `_ensure_dbt_secret` independently resolves the analytics cluster's primary pod (its own `_kubectl_cluster_primary_pod` call) rather than assuming any state left behind by `_ensure_etl_secrets` — matches the codebase's existing precedent in `_ensure_grafana_secrets`, which also resolves the primary pod fresh for its own `grafana_reader` password. This makes `_ensure_dbt_secret`'s subprocess-call shape two calls (get-cluster + exec-psql), the same shape `_ensure_etl_secrets`'s own `etl/analytics-db` block and `_ensure_grafana_secrets`'s own `grafana/analytics-db` block both already use.
- The `_ensure_policy`/`_ensure_kubernetes_role`/`_ensure_dbt_secret` triple was inserted immediately after the csv-processor block and before the airflow block in `bootstrap()`, keeping all three dbt-setup calls grouped together (the plan noted either position relative to the airflow block was acceptable).
