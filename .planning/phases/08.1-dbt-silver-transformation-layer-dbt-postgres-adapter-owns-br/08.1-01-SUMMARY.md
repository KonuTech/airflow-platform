# Phase 08.1 Plan 01: PostgreSQL Foundation — dbt_app Role, Bronze/Silver Tables Summary

**Three Alembic migrations (0021-0023) creating the least-privilege `dbt_app` PostgreSQL role, durable bronze tables `staging.customers`/`staging.orders`, and `silver.customers`/`silver.orders` with a real database-level UNIQUE constraint on each business key — live-proven via a direct duplicate-key INSERT raising `psycopg.errors.UniqueViolation`.**

## Accomplishments
- `dbt_app` role created with the exact D-08 boundary: SELECT-only on `staging` (via `ALTER DEFAULT PRIVILEGES` so the grant applies automatically once 0022 creates the tables), full ownership of the new `silver` schema, and zero grant anywhere on `normalized`/`meta`
- Durable, LOGGED, cumulative bronze tables `staging.customers`/`staging.orders` — deliberately never `UNLOGGED` (Pitfall 4), no business-key uniqueness (bronze allows duplicates, D-07), `SELECT, INSERT` only for `etl_app` (raw-immutability extended to bronze)
- `silver.customers`/`silver.orders` with a real `UNIQUE` constraint on `customer_id`/`order_id` (D-14) — Alembic-owned DDL, not dbt's own materialization, so a later plan's lineage-view extension can reference these tables before dbt ever runs
- Full `alembic upgrade head` → `downgrade base` → `upgrade head` cycle proven clean against a throwaway PostgreSQL 18 (live-verified, not merely asserted)
- Live-verified: `pg_class.relpersistence = 'p'` (permanent/LOGGED) for both staging tables; `silver.customers` table owner is `dbt_app`; a direct duplicate-`customer_id`/`order_id` INSERT into silver raises `psycopg.errors.UniqueViolation`

## Decisions Made
- Lineage columns (`_run_id`/`_file_id`/`_batch_id`/`_source_row_number`/`_record_hash`/`_record_hash_version`) on both new tables include explicit `ForeignKey`s to `meta.ingestion_runs`/`meta.files`/`meta.batches`, mirroring migration 0005's established table-shape convention (identity PK, business columns, six lineage columns each with an explicit ForeignKey, `_ingested_at` server_default now()) rather than the plan interfaces' bare type-tuple reading literally
- `_lineage_columns()` is a per-call factory function, not a module-level tuple, in both 0022 and 0023 — a `sa.Column` instance binds to whichever `Table` it is first attached to, so reusing the same instances across two `op.create_table()` calls in one migration would raise "Column object already assigned to Table"
- Migration 0021's `downgrade()` uses `DROP SCHEMA silver` (not `ALTER SCHEMA silver OWNER TO ...`) since by the time 0021's downgrade runs in a full `downgrade base` sweep, 0023's downgrade has already dropped both silver tables, leaving the schema empty and safe to drop outright — one of the two options the plan's action text explicitly permitted

## Deviations from Plan

None — plan executed exactly as written. Two minor, in-scope lint fixes were applied during implementation (both Rule 1 - Bug, auto-fixed inline, no separate commit needed beyond the task commits they landed in):

1. **[Rule 1 - Bug] Docstring line length exceeded ruff's 100-char limit in migration 0021's `downgrade()`** — shortened the docstring wording; committed as part of Task 2's commit (`c02d41c`) since it was discovered while linting the newly-added Task 2 file.
2. **[Rule 1 - Bug] SQLAlchemy Column-object reuse across two `op.create_table()` calls** — the initial draft of migration 0022 defined lineage columns as a shared module-level tuple; SQLAlchemy raises `"Column object 'x' already assigned to Table"` when the same `Column` instance is attached to a second `Table`. Fixed by converting the tuple into a `_lineage_columns()` factory function called fresh for each table. Verified by running `pytest tests/integration/test_migrations.py` (which exercises `alembic upgrade head` end-to-end) before committing Task 2.
