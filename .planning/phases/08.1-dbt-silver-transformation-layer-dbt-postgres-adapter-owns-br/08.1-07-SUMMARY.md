**Independent `meta.run_stages` claim/heartbeat/complete cycle (D-17) plus a sixth `pipeline_version` idempotency-key term with `replay_of_run_id` wiring (D-18), making historical `SUCCEEDED` files re-claimable under the new 3-stage pipeline.**

## Accomplishments

- `MetadataRepository`/`PostgresMetadataRepository` gained five new methods (`claim_run_stage`, `heartbeat_run_stage`, `complete_run_stage`, `get_run_stage_status`, `list_staged_run_ids`) giving `publish_ingest` (plan 08.1-10) a fully independent claim/heartbeat/complete cycle against `meta.run_stages`, gated so a run whose stage hop has not genuinely reached `STAGED` can never be claimed for publish.
- `create_ingestion_run`/`get_or_create_ingestion_run` extended with a keyword-only, defaulted `replay_of_run_id` parameter, plus a new `find_latest_succeeded_run_for_file` lookup method — every existing call site keeps compiling unchanged.
- `discovery.py`'s idempotency-key formula extended with a sixth, append-only `pipeline_version` term (`_PIPELINE_VERSION = "2"`), with a `find_latest_succeeded_run_for_file` lookup wired into both `_process_ungrouped_object` and `_process_multipart_group` immediately before each allocates its run — a file already `SUCCEEDED` under the OLD 5-term formula becomes a real, newly-claimable `DiscoveredUnit` with `replay_of_run_id` correctly set.
- Two new integration test files (`test_claim_lease_split.py`, `test_backfill_idempotency.py`) prove all documented behaviors against a real, migrated testcontainers PostgreSQL + MinIO.

## Decisions Made

- `claim_run_stage`'s SQL puts the `meta.ingestion_runs.status = 'STAGED'` cross-table guard inside the `INSERT`'s own `WHERE EXISTS` clause governing the source `SELECT`, rather than a separate pre-check query — this makes the guard apply correctly even on a first-ever claim, when no `run_stages` row exists yet to gate the `ON CONFLICT` branch against.
- `get_or_create_ingestion_run`'s `ON CONFLICT ... DO UPDATE SET` clause deliberately excludes `replay_of_run_id` — it is a first-insert-only value; a repeat call's argument (which its caller does not necessarily recompute identically) must never silently clear the lineage already recorded on the row.
- `_PIPELINE_VERSION` follows `_FILE_HASH_VERSION`'s existing "bump this constant to signal a change" convention rather than inventing a new mechanism.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `_FakeMetadataRepository` test doubles broke at runtime after discovery.py started calling `find_latest_succeeded_run_for_file`**

- **Found during:** Task 3, running the existing `tests/unit/` suite after wiring `discover_files`'s new lookup call
- **Issue:** Two separate in-memory `_FakeMetadataRepository` doubles (`tests/unit/test_discovery.py` and `tests/unit/validate/test_batch_complete_marker.py`) implement only the subset of `MetadataRepository` that `discover_files` was previously known to call. Once `_process_ungrouped_object`/`_process_multipart_group` started calling `metadata.find_latest_succeeded_run_for_file(...)` unconditionally, every test using either fake raised `AttributeError` — a real regression, not a test artifact, since the fakes are meant to mirror the real repository's contract as it's actually exercised.
- **Fix:** Added `find_latest_succeeded_run_for_file` (mirroring the real repository's `ORDER BY run_id DESC LIMIT 1` semantics) and a `replay_of_run_id` keyword to `get_or_create_ingestion_run` on both fakes, storing `file_id`/`replay_of_run_id` on the fakes' `_FakeRunRow` dataclass so the lookup has something real to match against.
- **Files modified:** `tests/unit/test_discovery.py`, `tests/unit/validate/test_batch_complete_marker.py`
- **Verification:** `uv run pytest tests/unit/ -q` — 494 passed (was 10 failed / 2 failed across the two files before the fix)
- **Committed in:** `abf7221` (Task 3 commit)
