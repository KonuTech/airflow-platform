<objective>
Complete two independent pieces of D-12/D-13's physical-schema work: extend
`meta.v_customers_lineage` to bridge the new dbt/silver hop (D-12, extending OBS-07 which stays
Phase 7/Complete in `REQUIREMENTS.md`'s traceability table — this plan implements the extension,
never re-claims the ID), and add supporting indexes to `normalized.customers`/`normalized.orders`
for time-range, point-lookup and ad-hoc business-usage queries (D-13).

**A genuine technical constraint this plan resolves, not a scope reduction** (D-13 asked for
"partitioning and indexing"; this plan delivers indexing only, with the reasoning below): Postgres
declarative table partitioning REQUIRES every unique constraint on a partitioned table to include
the partition key column(s). `MergePublisher`/`OrdersMergePublisher`'s existing `ON CONFLICT
(customer_id)`/`ON CONFLICT (order_id)` — which D-13 explicitly requires to stay unchanged —
depends on a UNIQUE constraint on exactly that one column. Range-partitioning `normalized.orders`
by `order_date` (the only genuinely time-range-shaped column available) would force the unique
constraint to become `(order_id, order_date)`, which would silently let a correction changing an
existing order's `order_date` insert a SECOND row instead of updating the first — a real,
first-class duplicate-business-key bug, the exact failure class this platform's whole architecture
exists to prevent. This is the same class of discovery that ruled out dbt's `merge` strategy for
silver (a real Postgres mechanic conflicting with an existing correctness guarantee) — the
response here is the same: choose the mechanism that preserves correctness (indexes) over the one
that would silently violate it (partitioning), and document why.

Purpose: this closes out D-12/D-13, the last two decisions from `08.1-CONTEXT.md` not yet covered
by an earlier plan in this phase.
Output: migrations 0026 (lineage view) and 0027 (gold indexes), plus test coverage.
</objective>
