<objective>
Split `run_ingest` into `stage_ingest` and `publish_ingest` (D-04), reusing every already-proven
mechanism from today's function verbatim wherever it still applies, and relocating the
referential-integrity/circuit-breaker/volume-anomaly/rejected-records/validation-report logic to
its new, more correct home: staging time, not publish time (a genuine consequence of D-04's split,
not incidental scope creep — see this plan's own reasoning below).

**Why the quality-gate logic moves to `stage_ingest`, concretely:** today, `_apply_referential_barrier`
and the circuit breaker run inside `run_ingest`'s publish transaction, filtering rows out of the
PER-RUN SCRATCH staging table immediately before the publish `SELECT` reads it. After this plan,
that scratch table's entire lifecycle (create → COPY → promote → drop) collapses into
`stage_ingest` alone (plan 08.1-06's `promote_to_durable_bronze`) — by the time `publish_ingest`
ever runs, the scratch table is long gone, and `publish_ingest` may be finalizing SEVERAL
`stage_ingest` runs' worth of dbt-consolidated silver data in one pass, so a per-run filtering
step no longer has a single scratch table to operate against. Filtering at staging time — before
any of it reaches durable bronze — is also strictly *more* correct: bad data never even enters the
append-only, cumulative bronze table dbt reads from. `resolve_rejected_records_for_business_keys`
is the ONE exception that stays in `publish_ingest`: it must use `published_business_keys` from
the actual publish result (a publish-time-only concept, CR-01's own already-proven reasoning),
never from rows that merely survived staging.

**`publish_ingest`'s new shape** (RESEARCH.md Open Question 1, fully resolved by plan 08.1-07's
`meta.run_stages`/`list_staged_run_ids` machinery): a single, unmapped invocation per dataset —
never per-run — because dbt's own watermark-driven batching (D-05) may consolidate several
`stage_ingest` runs' bronze contributions into one deduplicated silver pass. It queries
`silver.<dataset>` unconditionally (the SAME idempotent `INSERT ... ON CONFLICT` upsert `merge.py`
already proves safe to re-run), then finalizes every currently-`STAGED` run in one atomic
transaction.

Purpose: this is where D-02/D-04's architectural restructuring actually lands in code — every
other plan in this wave built a piece this plan assembles.
Output: `pipeline/run.py` with `run_ingest` replaced by `stage_ingest`/`publish_ingest`, plus
integration tests for both.
</objective>
