<objective>
Build the two pieces of metadata-layer machinery `pipeline/run.py`'s split (plan 08.1-10) depends
on: D-17's independent claim/heartbeat/complete cycle for `meta.run_stages`, and D-18's
idempotency-key/`replay_of_run_id` extension that makes historical (already-`SUCCEEDED`) files
legitimately re-claimable under the new 3-stage pipeline.

**D-17's exact mechanism** (RESEARCH.md Open Question 1, resolved here): `stage_ingest` keeps
using the EXISTING, unmodified `claim_ingestion_run`/`heartbeat_ingestion_run` against
`meta.ingestion_runs` (no change to that table's claim semantics) and, on success, transitions
the run to a NEW terminal-for-its-hop status, `'STAGED'`, via the ALREADY-EXISTING generic
`update_ingestion_run_status` — zero new repository methods needed for that half. `publish_ingest`
gets its OWN, fully independent claim against `meta.run_stages`, gated by a join condition
requiring `meta.ingestion_runs.status = 'STAGED'` — this is what prevents a retried `stage` task
and a live `publish` claim from ever colliding on the same lease, the exact race Pitfall 2 warns
against.

**D-18's exact mechanism** (Pitfall 1, resolved here): `discovery.py`'s idempotency-key formula
gains a sixth, append-only term — `pipeline_version` — bumped from its implicit "1" (the original
2-stage pipeline) to `"2"` (this phase's 3-stage pipeline). Before creating a run under the new
key, `discover_files` looks up whether an OLDER-formula run for the same `file_id` already
`SUCCEEDED`, and if so passes its `run_id` as `replay_of_run_id` on the new row — the
already-existing, currently-unused column this was reserved for.

Purpose: without this plan, `stage_ingest`/`publish_ingest` (08.1-10) have no way to independently
claim their own hop, and D-16's backfill (08.1-13) has no way to make historical files claimable
at all.
Output: five new `MetadataRepository` Protocol methods + `PostgresMetadataRepository`
implementations, `discovery.py`'s idempotency-key extension, and two new integration tests.
</objective>
