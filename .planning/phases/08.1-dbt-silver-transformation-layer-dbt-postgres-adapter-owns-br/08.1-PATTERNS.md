## Pattern Assignments

### 1. dbt project scaffolding — `dbt/**` (new territory)

No analog exists in this repository — this is the first dbt project. Use RESEARCH.md's own
Architecture Patterns 1-3 (`08.1-RESEARCH.md`, "Architecture Patterns" section) as the primary
source, each already `[CITED]` against official dbt docs:

- **Pattern 1** (non-event-time incremental cursor, D-06) — the `is_incremental()` + `_run_id`
  watermark shape, verbatim in RESEARCH.md.
- **Pattern 2** (atomic post-hook audit write, D-09) — the `post_hook` INSERT shape.
- **Pattern 3** (native `contract`/`constraints`, D-14) — the `schema.yml` DDL-generating shape.

**Conceptual analog for the dedup SQL shape** (not a literal copy — different engine):
`packages/dataplat/src/dataplat/load/publish/merge.py` lines 50-72 already solved "dedup a
source containing duplicate business keys, deterministically, by latest `event_ts`" in raw SQL:

```sql
-- packages/dataplat/src/dataplat/load/publish/merge.py, lines 56-61
SELECT DISTINCT ON (customer_id)
       customer_id::int, name, country, birth_date::date, event_ts::timestamptz,
       _run_id, _file_id, _batch_id, _source_row_number,
       _record_hash, _record_hash_version
FROM   {staging_table}
ORDER  BY customer_id, event_ts DESC, _source_row_number DESC
```

The dbt incremental model's own `row_number() over (partition by customer_id order by event_ts
desc, _source_row_number desc)` (RESEARCH.md Pattern 1) is the *same tie-break rule*
(`event_ts DESC, _source_row_number DESC`), reimplemented as a window function because Postgres
has no `QUALIFY` clause and `DISTINCT ON` cannot be expressed inside a dbt incremental model's
`{{ config(...) }}` block the same way. **Carry the exact tie-break column order forward** —
`event_ts DESC, _source_row_number DESC` is this platform's one existing "who wins a duplicate
business key" rule (README §26/§27); do not invent a different tie-break in the dbt model.

**Column/business-key declaration shape** to mirror in `dbt/models/staging/_sources.yml` and
`dbt/models/silver/schema.yml`, from `configs/datasets/customers.yaml` lines 98-122:

```yaml
# configs/datasets/customers.yaml, lines 98-104
columns:
  - name: customer_id
    type: string
    nullable: false
    required: true
    business_key: true
    description: "Natural business key for a customer record"
```

The six lineage columns every silver/gold row must carry (D-11) are `staging.py`'s own
`_LINEAGE_COLUMN_TYPES` constant, verbatim:

```python
# packages/dataplat/src/dataplat/load/staging.py, lines 125-133
_LINEAGE_COLUMN_TYPES: tuple[tuple[str, str], ...] = (
    ("_run_id", "bigint"),
    ("_file_id", "bigint"),
    ("_batch_id", "bigint"),
    ("_source_row_number", "bigint"),
    ("_record_hash", "bytea"),
    ("_record_hash_version", "smallint"),
)
```

Copy the entire multi-stage shape (builder/runtime split, `uv sync --frozen` before source
exists then `--locked --no-editable` after, non-root numeric UID, `GIT_SHA` OCI labels,
never `:latest`). Full file read; every numbered comment block is load-bearing, not stylistic.

**Layer ordering + dependency-only sync** (`docker/csv-processor/Dockerfile` lines 60-80):
```dockerfile
ARG GIT_SHA=unknown
```

**Adapt for dbt** (per RESEARCH.md's Standard Stack + Anti-Patterns): this image installs

member — no `packages/dbt/pyproject.toml` to COPY), copies in `dbt/` (the project directory)
the same way this Dockerfile copies `configs/` (lines 82-86, after the dependency-resolution
layer so a project-only change never invalidates the dependency cache), and contains **no**
`dataplat`/`csv_processor`/`apache-airflow` (Anti-Patterns: three single-purpose images, never
two — ADR-0004's discipline extended to a third image).

### 3. `docker/dbt/resolve_secrets.py` — secret resolution across a second, independent image

**Two source patterns to combine, never merged into one shared library** (RESEARCH.md
Architecture Pattern 4 + Don't Hand-Roll table — this is a deliberate duplication, matching an
already-established precedent in this codebase, not an oversight):

**(a) The `vault://mount/path#field` parsing logic to duplicate**
(`packages/dataplat/src/dataplat/secrets/resolver.py` lines 33-56, 91-111):
```python
# _vault_client() — lazy, cached, SA-token Kubernetes-auth login
def _vault_client() -> hvac.Client:
    global _client
    if _client is None:
        client = hvac.Client(url=os.environ["VAULT_ADDR"])
        token_path = Path("/var/run/secrets/kubernetes.io/serviceaccount/token")
        client.auth.kubernetes.login(
            role=os.environ["VAULT_K8S_ROLE"],
            jwt=token_path.read_text(encoding="utf-8"),
        )
        _client = client
    return _client

# vault:// scheme parsing, inside resolve_secret(ref)
if parsed.scheme == "vault":
    mount_point = parsed.netloc
    path = parsed.path.lstrip("/")
    field = parsed.fragment
    if not (mount_point and path and field):
        msg = f"malformed vault:// ref (need scheme://mount/path#field): {ref!r}"
        raise SecretResolutionError(msg, context={"ref": ref})
    secret = _vault_client().secrets.kv.v2.read_secret_version(
        mount_point=mount_point, path=path,
    )
    return str(secret["data"]["data"][field])
```

**(b) Why this must be a standalone duplicate, not an import** — the exact precedent this
project already established for the identical cross-boundary problem, from
`airflow/dags/_common/integrity_gate.py` module docstring lines 30-34:
```
`_reject_file` is therefore the ONE sanctioned exception to ADR-0004's "Airflow never
writes to the analytical database directly" rule -- a narrow, explicit inline `psycopg`
INSERT, never a `dataplat` import; the SQL shape below is duplicated from
`get_or_create_dataset`/`create_file` (`packages/dataplat/src/dataplat/metadata/postgres.py`),
not imported from it.
```
Apply identically in reverse: the dbt image writes a standalone script (a few dozen lines,
`hvac` direct) that resolves five separate `vault://etl/dbt-db#{host,port,user,password,dbname}`
references into plain env vars (`DBT_PG_HOST`, `DBT_PG_USER`, etc.) that `profiles.yml`'s
`env_var()` calls then read — run as the pod's `cmds` entrypoint, before `dbt build` starts.
Never `pip install dataplat` into this image to reuse `resolve_secret()` directly (Anti-Patterns
table — recreates exactly the coupling ADR-0004 avoids in the other direction).

### 4. Migrations — role/grant, table DDL, audit DDL, state-machine DDL, view

**4a. `0021_dbt_app_role_silver_schema.py` — exact analog: `migrations/versions/0011_grafana_reader_role.py`**

Full file (57 lines) — the first `CREATE ROLE` migration this project wrote, and its own
docstring explains why `op.execute()`-only DDL is used (no `postInitApplicationSQL` path since
the cluster is already running):

```python
# migrations/versions/0011_grafana_reader_role.py, lines 42-57
def upgrade() -> None:
    """Create `grafana_reader`, grant schema USAGE, then SELECT on exactly three tables."""
    op.execute("CREATE ROLE grafana_reader LOGIN")
    op.execute("GRANT USAGE ON SCHEMA meta TO grafana_reader")
    op.execute("GRANT USAGE ON SCHEMA normalized TO grafana_reader")
    op.execute("GRANT SELECT ON meta.datasets, meta.files, meta.ingestion_runs TO grafana_reader")


def downgrade() -> None:
    """Revoke every grant this migration added, then drop the role (reverse of `upgrade()`)."""
    op.execute("REVOKE SELECT ON meta.datasets, meta.files, meta.ingestion_runs FROM grafana_reader")
    op.execute("REVOKE USAGE ON SCHEMA normalized FROM grafana_reader")
    op.execute("REVOKE USAGE ON SCHEMA meta FROM grafana_reader")
    op.execute("DROP ROLE grafana_reader")
```

**Critical sequencing lesson to apply** (this project has been burned by getting this wrong
once — `migrations/versions/0008_grant_schema_usage_to_etl_app.py` lines 1-27 docstring):
schema-level `USAGE` is a hard prerequisite gate before any table-level grant takes effect at
all — a table grant with no schema `USAGE` is silently inert. `0007_staging_schema.py` got the
two-part sequence right the first time (lines 39-42):
```python
def upgrade() -> None:
    """Create schema `staging`; grant `etl_app` USAGE + CREATE (it DDLs its own tables here)."""
    op.execute("CREATE SCHEMA IF NOT EXISTS staging")
    op.execute("GRANT USAGE, CREATE ON SCHEMA staging TO etl_app")
```
`dbt_app` needs the identical two-part shape twice: `GRANT USAGE ON SCHEMA staging TO dbt_app`
+ `GRANT SELECT ON ALL TABLES IN SCHEMA staging TO dbt_app` (+ `ALTER DEFAULT PRIVILEGES`, since
new dataset tables land in `staging` over time — D-08's read-only bronze access), then
`CREATE SCHEMA silver` + `GRANT USAGE, CREATE ON SCHEMA silver TO dbt_app` (dbt DDLs its own
tables here, the same shape `staging`/`etl_app` already established) — **never** `USAGE` on
`normalized`/`meta` (D-08's hard boundary: dbt never reads gold, never writes `meta` directly
outside its own `meta.dedup_audit` insert, which needs a narrower, separate grant — see 4c).
Password is set out-of-band via Vault bootstrap, never embedded (matches 0011's own documented
reasoning verbatim — see Section 6 below).
