<objective>
Complete the control-plane metadata schema this phase needs: `meta.dedup_audit` +
`meta.dedup_decisions` (D-09's dbt-writes-its-own-audit-trail design, DEDUP-04) and
`meta.run_stages` (D-17's two-phase claim, pulled forward from Phase 9's original ARCHITECTURE.md
design because a 3-task pipeline split needs somewhere to record progress between `stage` and
`publish`).

**Schema-shape correction this plan makes concrete** (RESEARCH.md Pattern 2 flags this tension
explicitly): the original ARCHITECTURE.md sketch (line 238) assumed one `meta.dedup_audit` row
per bronze `run_id` — a 1:1 assumption from Phase 9's now-superseded design. D-05's watermark-
driven dbt batching breaks that: one `dbt build` invocation can span multiple bronze commits. This
plan uses dbt's own `invocation_id` (a UUID Jinja exposes) as the row identity, with a
`min_run_id`/`max_run_id` range instead of a single FK.

Purpose: plan 08.1-08 (dbt scaffolding) writes into `meta.dedup_audit`/`meta.dedup_decisions` via
a post-hook; plan 08.1-07 (repository.py) and 08.1-10 (run.py split) build the claim/heartbeat
methods against `meta.run_stages`.
Output: migrations 0024 and 0025, plus extended migration tests.
</objective>
