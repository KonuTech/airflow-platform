<objective>
Create the physical PostgreSQL foundation the whole phase builds on: a least-privilege `dbt_app`
role, the new durable (LOGGED, cumulative) bronze tables `staging.customers`/`staging.orders`
(D-01), and the new `silver` schema's physical tables `silver.customers`/`silver.orders` with a
real database-level UNIQUE constraint on each dataset's business key (D-14).

**Architectural decision this plan makes concrete** (flagged as an open sequencing question by
RESEARCH.md Pitfall 4 and Pattern 3, not fully resolved there): silver's tables are created by
**Alembic, not by dbt's own materialization**. This is required because a later migration
(08.1-09) extends `meta.v_customers_lineage` with `LEFT JOIN silver.customers` — a `CREATE VIEW`
that references a table only dbt would create cannot run before dbt's first execution, and
migrations must all apply cleanly at deploy time, before any DAG has ever run. Alembic owning the
silver DDL (mirroring how it already owns `normalized.customers`/`normalized.orders`) also gives
D-14's "hard constraint, not just dbt's `unique_key` logic" its strongest form: the constraint
exists from the very first deploy, not merely after dbt's first successful build. dbt's incremental
model (plan 08.1-08) targets this pre-existing table via `contract: enforced: true`, which
*validates* the model's column list against the table rather than creating it.

Purpose: every later plan in this phase (dbt scaffolding, the Python pipeline split, the lineage
view extension) depends on this physical schema already existing and being correctly
least-privilege-scoped.
Output: three new Alembic migrations (0021, 0022, 0023) and an extended `test_migrations.py`.
</objective>
