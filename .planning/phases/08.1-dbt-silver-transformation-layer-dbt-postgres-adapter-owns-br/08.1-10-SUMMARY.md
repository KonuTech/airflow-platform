# Phase 08.1 Plan 10: stage_ingest/publish_ingest split Summary

**Split `run_ingest` into `stage_ingest` (claim/stage/quality-gate/promote-to-bronze, terminal status `STAGED`) and `publish_ingest` (claim every STAGED run for a dataset, publish `silver.<dataset>` into `normalized.<dataset>` via the unchanged advisory-lock+Publisher mechanism, finalize all claimed runs atomically) -- D-02/D-04's architectural restructuring now lands in code.**

## Performance

- **Duration:** ~50 min
- **Tasks:** 2 completed
- **Files modified:** 4 (2 modified, 2 created)

## Accomplishments

- `stage_ingest()` reproduces every pre-existing correctness guarantee (idempotency, quality gating, heartbeat, tracing, VALID-04 report artifact) up through durable-bronze promotion, with the referential/circuit-breaker/volume-anomaly quality gate now running strictly BEFORE `promote_to_durable_bronze` on the same connection as the scratch-buffer COPY -- a tripped `QualityThresholdExceeded` rolls back the COPY too, so bad data never reaches durable bronze (proven live, not just designed).
- `publish_ingest()` is a genuine single-dataset, multi-run-capable finalize pass: zero STAGED runs is a cheap no-op (no connection opened at all); N STAGED runs (proven with N=2) finalize together in one atomic transaction, each getting its own `meta.run_stages` PUBLISH-stage claim/complete cycle; a second call immediately after is idempotent (proven: identical `normalized.customers` row count and content).
- `run_ingest` is fully removed from `dataplat.pipeline.run` -- `grep -n "def run_ingest"` returns no match, matching the plan's own acceptance criterion.

## Decisions Made

- **`_skipped_receipt`'s `'STAGED'` handling** (Task 1's own Test 3, explicitly left as a decision for the executor to make and justify): extended the existing `SUCCEEDED`-only skip-status mapping to also treat `'STAGED'` as `SKIPPED_DUPLICATE`, rather than leaving it to raise `DataPlatformError`. Rationale: `claim_ingestion_run`'s claimability `WHERE` clause (`status IN ('PENDING','FAILED') OR (status='RUNNING' AND lease expired)`) structurally excludes `'STAGED'` the exact same way it excludes `'SUCCEEDED'` -- both statuses mean "this run's own scoped work already genuinely completed", so refusing the claim and reporting a duplicate (not an error) is the correct, non-surprising behavior for a retried `stage` pod invocation against an already-staged run.
- **`publish_ingest`'s aggregate per-pass metric attribution**: `rows_loaded` (from `result.rows_affected`) and `resolve_rejected_records_for_business_keys`' `resolved_by_run_id` (`max(finalized_run_ids)`) are both PASS-level, not per-run, values when one invocation finalizes several `STAGED` runs -- `merge.py`'s `_PUBLISH_SQL` has no per-run filter and changing that is explicitly out of this plan's scope (08.1-06's "merge.py's own SQL text requires ZERO change" constraint). Documented explicitly at the `finalize_publication` call site (a hard acceptance criterion of this plan) rather than left as a silent gap, mirroring the codebase's own pre-existing `rows_deduplicated` imprecision precedent.
