# Phase 08.1: dbt Silver Transformation Layer - Context

**Gathered:** 2026-08-18
**Status:** Ready for planning

<domain>
## Phase Boundary

A dbt (Postgres adapter) bronze-to-silver transformation stage: a new persisted `silver` schema
in the analytical PostgreSQL, populated by dbt models that clean, deduplicate (business-key
primary + exact-row-hash secondary, both applied within-file and across-file/batch/run), and
resolve late-arriving/out-of-order events using event/business timestamp — while the existing
Python `MergePublisher`/`OrdersMergePublisher` continue to own the atomic silver-to-gold publish
inside the single META-03 transaction (`pg_advisory_xact_lock` + `INSERT ... ON CONFLICT`),
unchanged in mechanism.

Bronze ingestion (Phases 1-8: CSV parsing, encoding/dialect detection, schema contracts, file
integrity, quarantine) is untouched — dbt never touches raw file ingestion. Phase 10's SCD2 stays
entirely Python-owned; `dbt snapshot` is explicitly rejected there for the same structural reason
gold stays Python-owned here (dbt's per-model transactions can't participate in META-03's
single-transaction guarantee).

Full reasoning for dbt being back in scope, narrowly: `.planning/notes/dbt-silver-layer-architecture-decision.md`.

</domain>

<decisions>
## Implementation Decisions

### Bronze Persistence & Pipeline Shape

- **D-01:** Bronze becomes a stable, cumulative, append-only table per dataset — not today's
  per-run throwaway `staging.<dataset>__r<run_id>` UNLOGGED table. dbt sources it incrementally
  via a normal dbt `source()`. Matches README §4.2's "append-only landing tables" language. The
  existing per-run UNLOGGED table becomes a scratch COPY buffer that gets appended into this
  durable table, then dropped as today.
- **D-02:** dbt runs as its own DAG task with its own native incremental idempotency (re-running
  with nothing new to process is a no-op by construction) — decoupled from the Python
  claim/lease/heartbeat mechanism that currently wraps `run_ingest`'s stage+publish as one unit.
  The claimed run still covers claim→stage→publish (now reading from silver instead of staging);
  META-03's transactional guarantee is untouched.
- **D-03:** One connected DAG per dataset: sensor → bronze stage → dbt build (silver) → Python
  publish (gold) — not split across multiple DAGs.
- **D-04:** The existing single `ingest` task/CLI invocation splits into 3 distinct DAG tasks:
  stage bronze → dbt build → publish gold (replacing today's one `dataplat ingest` call that does
  staging+publish together).
- **D-05:** dbt's incremental model is watermark-driven ("everything new since last processed"),
  not invoked scoped to one specific `run_id` — the idiomatic dbt incremental pattern, and
  self-healing if dbt lags behind or multiple bronze commits land before it next runs.
- **D-06 (hard correctness constraint):** dbt's incremental filter MUST key off an ingestion-side
  monotonic marker (`_run_id`/`_batch_id`/load timestamp) — **never** off `event_ts`. A naive
  `WHERE event_ts > max(event_ts)` filter would silently drop a record arriving today with a
  3-month-old `event_ts` — exactly the late-arriving case this phase exists to handle. `event_ts`
  is used only to resolve correct ordering/final-state AMONG rows within an incremental batch,
  never to decide which rows to pull.
- **Research-flagged, not decided here:** which dbt-postgres incremental materialization strategy
  silver itself should use (`merge`/`delete+insert`/`append`) and its concurrency safety for
  silver specifically — the architecture note already flags this as needing live proof, not a
  judgment call made in this discussion.

### Dedup Ownership

- **D-07:** dbt owns BOTH layers of the dedup strategy already locked in Phase 9's paused
  discussion — business-key dedup (primary) AND exact-row-hash dedup (secondary), both applied at
  every scope (within-file, cross-file, cross-batch, cross-run). Silver IS the fully-deduplicated
  layer. The Phase 9 Python `DeduplicationStage` is never built.
- **D-08:** Cross-run dedup compares incoming rows against silver's own accumulated history
  (silver is now persisted/cumulative) — NOT against gold (`normalized.customers/orders`)
  directly. dbt's Postgres role needs read access to staging (bronze) + write access to silver —
  never read access to gold/normalized. This supersedes Phase 9 checkpoint's original answer
  (which assumed only gold was persisted, before silver existed).
- **D-09:** dbt writes `meta.dedup_audit` directly — a dbt model/macro/post-hook inserts audit
  rows as part of the same transform, in the same transaction as the silver write — not a Python
  step parsing dbt's run artifacts afterward. `meta.dedup_audit` has no migration yet; this phase
  creates it (design already sketched in `.planning/research/ARCHITECTURE.md` lines 238, 273).
- **D-10:** `MergePublisher`'s existing late-arrival guard
  (`WHERE EXCLUDED.event_ts >= normalized.customers.event_ts`) stays in place as defense-in-depth
  at the gold layer, even though silver is already correctly ordered by dbt — consistent with the
  layered-defense philosophy applied throughout this discussion.
- **Carried-forward hard constraint** (from Phase 9's checkpoint, unchanged by this phase): a
  late event for a business key already seen in a later batch must always be recognized as
  stale/duplicate, never blindly re-applied.

### Silver Schema Shape & Lineage Bridging

- **D-11:** Silver passes through the same 6 lineage columns gold already has (`_run_id`,
  `_file_id`, `_batch_id`, `_source_row_number`, `_record_hash`, `_record_hash_version` — from
  `merge.py`'s SELECT list) unchanged, PLUS dbt-native audit columns on top (e.g. a
  `dedup_reason`/is-duplicate marker feeding `meta.dedup_audit`, dbt's own
  `_dbt_loaded_at`/`_dbt_updated_at` bookkeeping). Gold's publish SELECT should barely change —
  same columns, new FROM target (silver instead of staging).
- **D-12:** `meta.v_customers_lineage` (existing lineage view) gets extended in THIS phase to
  bridge the new dbt-owned silver hop explicitly, so "where did this row come from" resolves
  end-to-end without a gap at dbt's boundary.
- **D-13 (scope expansion beyond the original architecture note):** Gold's physical modeling —
  partitioning and indexing for business usage — IS in scope for 08.1, not deferred. This does
  **not** change gold's publish mechanism (Python `MergePublisher`, `INSERT ... ON CONFLICT`,
  single META-03 transaction stays exactly as-is) — only its physical DDL (partition strategy,
  indexes). Access patterns to balance (not mutually exclusive): time-range analytical queries
  (Grafana/BI, README §82), point lookups by business key (existing PK), and ad-hoc/exploratory
  analytical queries. Specific partition key/index tradeoffs are research/planning's call.
  **Resolved during planning (2026-08-18):** delivered as indexing-only, not partitioning. Postgres
  requires a partitioned table's UNIQUE constraint to include the partition key; the only
  genuinely time-range-shaped column (`order_date`/equivalent) would force the constraint from
  `UNIQUE (order_id)` to `UNIQUE (order_id, order_date)`, which would let a correction changing an
  existing order's date silently insert a second row instead of updating in place — a real
  duplicate-business-key bug. Explicitly re-confirmed with the user after a detailed walkthrough of
  this exact mechanic (partition-by-a-stable-column was also considered and rejected — it avoids
  the constraint conflict but delivers none of the time-range query benefit that was the actual
  motivation). Indexes on the relevant columns still make time-range queries fast, just without
  partition-pruning's storage-management side benefits (e.g. cheap old-partition drops).
- **D-14:** Silver's business key gets the same DB-level UNIQUE/PK constraint gold has (migration
  0006's precedent) — a structural guarantee, not just dbt's `unique_key` incremental-model logic.
  If dbt's dedup logic has a bug, it should hit a hard constraint violation rather than silently
  persisting duplicate rows in silver.

### Scope

- **D-15:** Both customers AND orders get dbt silver models in this phase (not customers-only
  first) — matches the symmetric treatment already locked in Phase 9's checkpoint for the
  now-superseded Python dedup interface. The dbt project structure (staging/silver source + model
  folders) is dataset-agnostic; building both against the same scaffolding now is less rework than
  bolting on orders later.
- **D-16:** This phase includes backfilling historical data through the new pipeline. Bronze (as
  newly defined — stable/cumulative, D-01) starts empty: the old per-run staging tables were
  already dropped after each historical publish, so there's no bronze history to carry over
  directly. But the raw CSV files are still immutable in MinIO (README §63) and gold already has
  rows from Phases 1-8. Use Airflow's backfill capability (README §33/§34: "backfills use the same
  pipeline, no simplified bypass") to re-run historical files through stage→dbt→publish, so silver
  ends up with a complete, correctly-deduplicated history matching gold — not just new data from
  08.1's ship date forward.

### Claim/Lease Architecture & Backfill Mechanism (added post-research, 2026-08-18)

Research (`08.1-RESEARCH.md`) surfaced two structural gaps between D-04's 3-task split and the
existing claim/lease mechanism, and between D-16's backfill intent and the existing idempotency
key. Both were escalated back to the user with research's own recommendations; both recommended
options were confirmed:

- **D-17:** Two-phase claim. `stage` claims, heartbeats, and completes independently (transitions
  to a new status, e.g. `STAGED`); `publish` performs its own SEPARATE claim/status transition when
  it picks up ready silver data. dbt's own task stays fully decoupled from the claim (matches D-02
  exactly — dbt was never meant to be inside the Python lease in the first place). This pulls
  `run_stages` (already designed in `.planning/research/ARCHITECTURE.md`'s "Correctness phase"
  table, originally slated for Phase 9) into THIS phase now, since a multi-stage state machine
  needs somewhere to record progress between `stage` and `publish`. Rejected alternative: a single
  lease spanning all 3 tasks, refreshed by each — would need a new cross-pod lease-refresh
  mechanism, and a lease surviving on behalf of a not-yet-running task is architecturally unusual
  (leases exist to detect a crashed worker, not to persist across a scheduled gap).
- **D-18:** Extend the idempotency-key formula with an append-only `pipeline_version` (or
  `target_schema_version`) term, matching `discovery.py`'s own documented convention for evolving
  the formula ("the first four terms are never reordered or replaced"). Historical files get a
  legitimately new, claimable `run_id` under the new 3-stage pipeline; the already-existing (but
  currently unused anywhere in the codebase) `replay_of_run_id` column links back to the original
  `SUCCEEDED` run for audit continuity. This becomes the platform's standing mechanism for any
  future pipeline-shape change, not a one-off fix. Rejected alternative: an explicit, scripted
  reset/replay operation mutating specific historical rows back to a reclaimable status — narrower
  blast radius for this one migration, but risks violating other code's implicit assumption that
  `SUCCEEDED` is permanent (lineage view joins, rejected-record resolution), and doesn't generalize.

### Claude's Discretion

- Exact dbt project scaffolding/tooling: dbt Core version (v2.0 alpha/Fusion vs. stable 1.x),
  Astronomer Cosmos vs. plain `KubernetesPodOperator` running `dbt build` for orchestration —
  explicitly left open by the architecture note ("Not decided here — planning's job").
- Which dbt-postgres incremental materialization strategy silver itself uses
  (`merge`/`delete+insert`/`append`) and proving its concurrency safety for silver specifically —
  flagged as a research question needing live proof, not a discussion judgment call.
- Exact task/CLI subcommand shape for the stage/dbt-build/publish split (e.g. whether
  `dataplat ingest` splits into `dataplat stage` + `dataplat publish`, or a new command set
  entirely).
- New `dbt` Postgres role's exact name and grant DDL — follow the existing
  `etl_app`/`analytics_owner`/`grafana_reader` least-privilege pattern (migrations 0008, 0019):
  read on staging, read+write on silver only, never on gold/normalized.
- Silver schema's literal name (recommend `silver`, matching README's exact terminology) and the
  new role's literal name (recommend following the `etl_app` convention, e.g. `dbt_app`).
- Exact partition key and index choices for gold's physical modeling (D-13), balancing the three
  named access patterns.
- Whether dbt models get their own dbt-native schema tests (`unique`, `not_null`, etc.) in
  `schema.yml`, given Phase 8's Python validation stage already validates bronze before dbt ever
  sees it.
