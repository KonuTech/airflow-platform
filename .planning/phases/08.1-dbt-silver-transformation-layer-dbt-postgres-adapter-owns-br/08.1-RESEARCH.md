## User Constraints (from CONTEXT.md)

### Locked Decisions

**Bronze Persistence & Pipeline Shape**

- **D-01:** Bronze becomes a stable, cumulative, append-only table per dataset — not today's
  per-run throwaway `staging.<dataset>__r<run_id>` UNLOGGED table. dbt sources it incrementally
  via a normal dbt `source()`. Matches README §4.2's "append-only landing tables" language. The
  existing per-run UNLOGGED table becomes a scratch COPY buffer that gets appended into this
  durable table, then dropped as today.
- **D-02:** dbt runs as its own DAG task with its own native incremental idempotency (re-running
  with nothing new to process is a no-op by construction) — decoupled from the Python
  claim/lease/heartbeat mechanism that currently wraps `run_ingest`'s stage+publish as one unit.
  The claimed run still covers claim→stage→publish (now reading from silver instead of staging);
  META-03's transactional guarantee is untouched.
- **D-03:** One connected DAG per dataset: sensor → bronze stage → dbt build (silver) → Python
  publish (gold) — not split across multiple DAGs.
- **D-04:** The existing single `ingest` task/CLI invocation splits into 3 distinct DAG tasks:
  stage bronze → dbt build → publish gold (replacing today's one `dataplat ingest` call that does
  staging+publish together).
- **D-05:** dbt's incremental model is watermark-driven ("everything new since last processed"),
  not invoked scoped to one specific `run_id` — the idiomatic dbt incremental pattern, and
  self-healing if dbt lags behind or multiple bronze commits land before it next runs.
- **D-06 (hard correctness constraint):** dbt's incremental filter MUST key off an ingestion-side
  monotonic marker (`_run_id`/`_batch_id`/load timestamp) — **never** off `event_ts`. A naive
  `WHERE event_ts > max(event_ts)` filter would silently drop a record arriving today with a
  3-month-old `event_ts` — exactly the late-arriving case this phase exists to handle. `event_ts`
  is used only to resolve correct ordering/final-state AMONG rows within an incremental batch,
  never to decide which rows to pull.
- **Research-flagged, not decided here:** which dbt-postgres incremental materialization strategy
  silver itself should use (`merge`/`delete+insert`/`append`) and its concurrency safety for
  silver specifically — the architecture note already flags this as needing live proof, not a
  judgment call made in this discussion.

**Dedup Ownership**

- **D-07:** dbt owns BOTH layers of the dedup strategy already locked in Phase 9's paused
  discussion — business-key dedup (primary) AND exact-row-hash dedup (secondary), both applied at
  every scope (within-file, cross-file, cross-batch, cross-run). Silver IS the fully-deduplicated
  layer. The Phase 9 Python `DeduplicationStage` is never built.
- **D-08:** Cross-run dedup compares incoming rows against silver's own accumulated history
  (silver is now persisted/cumulative) — NOT against gold (`normalized.customers/orders`)
  directly. dbt's Postgres role needs read access to staging (bronze) + write access to silver —
  never read access to gold/normalized. This supersedes Phase 9 checkpoint's original answer
  (which assumed only gold was persisted, before silver existed).
- **D-09:** dbt writes `meta.dedup_audit` directly — a dbt model/macro/post-hook inserts audit
  rows as part of the same transform, in the same transaction as the silver write — not a Python
  step parsing dbt's run artifacts afterward. `meta.dedup_audit` has no migration yet; this phase
  creates it (design already sketched in `.planning/research/ARCHITECTURE.md` lines 238, 273).
- **D-10:** `MergePublisher`'s existing late-arrival guard
  (`WHERE EXCLUDED.event_ts >= normalized.customers.event_ts`) stays in place as defense-in-depth
  at the gold layer, even though silver is already correctly ordered by dbt — consistent with the
  layered-defense philosophy applied throughout this discussion.
- **Carried-forward hard constraint** (from Phase 9's checkpoint, unchanged by this phase): a
  late event for a business key already seen in a later batch must always be recognized as
  stale/duplicate, never blindly re-applied.

**Silver Schema Shape & Lineage Bridging**

- **D-11:** Silver passes through the same 6 lineage columns gold already has (`_run_id`,
  `_file_id`, `_batch_id`, `_source_row_number`, `_record_hash`, `_record_hash_version` — from
  `merge.py`'s SELECT list) unchanged, PLUS dbt-native audit columns on top (e.g. a
  `dedup_reason`/is-duplicate marker feeding `meta.dedup_audit`, dbt's own
  `_dbt_loaded_at`/`_dbt_updated_at` bookkeeping). Gold's publish SELECT should barely change —
  same columns, new FROM target (silver instead of staging).
- **D-12:** `meta.v_customers_lineage` (existing lineage view) gets extended in THIS phase to
  bridge the new dbt-owned silver hop explicitly, so "where did this row come from" resolves
  end-to-end without a gap at dbt's boundary.
- **D-13 (scope expansion beyond the original architecture note):** Gold's physical modeling —
  partitioning and indexing for business usage — IS in scope for 08.1, not deferred. This does
  **not** change gold's publish mechanism (Python `MergePublisher`, `INSERT ... ON CONFLICT`,
  single META-03 transaction stays exactly as-is) — only its physical DDL (partition strategy,
  indexes). Access patterns to balance (not mutually exclusive): time-range analytical queries
  (Grafana/BI, README §82), point lookups by business key (existing PK), and ad-hoc/exploratory
  analytical queries. Specific partition key/index tradeoffs are research/planning's call.
- **D-14:** Silver's business key gets the same DB-level UNIQUE/PK constraint gold has (migration
  0006's precedent) — a structural guarantee, not just dbt's `unique_key` incremental-model logic.
  If dbt's dedup logic has a bug, it should hit a hard constraint violation rather than silently
  persisting duplicate rows in silver.

**Scope**

- **D-15:** Both customers AND orders get dbt silver models in this phase (not customers-only
  first) — matches the symmetric treatment already locked in Phase 9's checkpoint for the
  now-superseded Python dedup interface. The dbt project structure (staging/silver source + model
  folders) is dataset-agnostic; building both against the same scaffolding now is less rework than
  bolting on orders later.
- **D-16:** This phase includes backfilling historical data through the new pipeline. Bronze (as
  newly defined — stable/cumulative, D-01) starts empty: the old per-run staging tables were
  already dropped after each historical publish, so there's no bronze history to carry over
  directly. But the raw CSV files are still immutable in MinIO (README §63) and gold already has
  rows from Phases 1-8. Use Airflow's backfill capability (README §33/§34: "backfills use the same
  pipeline, no simplified bypass") to re-run historical files through stage→dbt→publish, so silver
  ends up with a complete, correctly-deduplicated history matching gold — not just new data from
  08.1's ship date forward.

## Summary

This phase introduces dbt into the platform for the first time, scoped narrowly to bronze→silver
(cleaning, deduplication, late-arriving-event resolution), landing in a new persisted `silver`
schema in the analytical PostgreSQL. Gold publish stays exactly as-is (Python `MergePublisher`/
`OrdersMergePublisher`, `pg_advisory_xact_lock` + `INSERT ... ON CONFLICT`, inside the single
META-03 transaction).

**Verified via PyPI registry (2026-08-18):** the current stable, non-alpha dbt stack is
**dbt-core 1.12.2** (released 2026-08-12) + **dbt-postgres 1.11.0** (released 2026-07-16). dbt
Core v2.0/Fusion is genuinely alpha (shipped 2026-06-01, explicitly "not yet GA" per dbt Labs'
own roadmap doc) — it must not be used for a phase whose Core Value is trust and traceability.
dbt-core and dbt-postgres now version independently (glued by shared `dbt-adapters`/`dbt-common`
packages), which is normal, current dbt architecture, not a mismatch to fix.

**Orchestration:** plain `KubernetesPodOperator` running `dbt build`, **not** Astronomer Cosmos.
Cosmos's per-model task rendering requires parsing the dbt project (`dbt ls` subprocess, "very
costly," or `manifest.json`, which "blocks the DAG processor for 50-100s") **inside the Airflow
scheduler/DAG-processor process** — a documented, current (2026) operational problem in Cosmos's
own issue tracker, and a direct conflict with this project's ORCH-06 ("DAG files... contain no
parsing") and ADR-0004 pattern (business logic only runs in a pod), compounded by this project's
own already-documented, repeatedly-hit CPU/scheduler-starvation history (STATE.md, multiple
resolved debug sessions). A single KPO running `dbt build` is lower-ceremony, matches the existing
`discover`/`ingest` KPO-per-stage pattern exactly, and reuses `common_kpo_kwargs()`/
`TracingKubernetesPodOperator` with zero new plumbing.

**Incremental strategy:** `delete+insert` with `unique_key` on the business key, **never**
`merge`. Verified directly (dbt-adapters source docs / DeepWiki mirror): dbt-postgres's `merge`
incremental strategy genuinely compiles to literal PostgreSQL `MERGE` (added in dbt v1.6, gated on
Postgres 15+ native `MERGE` support) — the exact statement type this project's own `MergePublisher`
already documents as unsafe under concurrent writers (PG BUG #18279). `delete+insert` structurally
cannot hit that specific bug (no insert/update branch race), fully satisfies D-07's upsert-like
dedup requirement via `unique_key`, and removes the design's dependence on "single-writer in
practice" holding forever — consistent with this project's own recurring "cheap now, unrecoverable
later" decision pattern (PITFALLS-driven reasoning throughout CLAUDE.md/PROJECT.md).

**Constraints:** dbt's own native `contract: enforced: true` + column/model-level `constraints:`
config (not the third-party `dbt_constraints` package) generates real Postgres `ALTER TABLE ADD
CONSTRAINT` DDL for `primary_key`/`unique`/`not_null`/`foreign_key`, and this applies to
`incremental` materializations, not just `table`. This directly satisfies D-14.

**The single most important non-obvious finding:** this project's existing idempotency mechanism
(`idempotency_key = sha256(dataset|content_sha256|config_hash|processor_image|schema_version)`,
verified in `discovery.py`) has **zero date/logical_date component** and explicitly treats a
`SUCCEEDED` run as permanently un-reclaimable (`claim_ingestion_run`'s `WHERE ... status IN
('PENDING','FAILED') OR (RUNNING AND lease expired)` — never `SUCCEEDED`). Every historical file
already has a `SUCCEEDED` `meta.ingestion_runs` row from Phases 1-8's two-stage pipeline. Simply
re-triggering the DAG (Airflow's classic backfill, or any re-run) will **not** reprocess those
files through the new stage→dbt→publish pipeline — `claim_ingestion_run` will refuse every one of
them and `_skipped_receipt` will return `SKIPPED_DUPLICATE` with **no staging attempted at all**.
D-16's backfill needs an explicit mechanism to give historical files a *new*, legitimately-claimable
run identity under the new pipeline shape — see Common Pitfalls and Open Questions.

**Primary recommendation:** dbt-core 1.12.2 + dbt-postgres 1.11.0, installed from scratch on this
project's existing `python:3.12-slim-bookworm` + `uv` Dockerfile pattern (not a dbt-labs published
image — their generic multi-adapter image is stale, capped at dbt-core 1.6.19); a single
`KubernetesPodOperator` task running `dbt build` between the existing `stage`/`ingest`-split tasks;
`delete+insert` incremental strategy with native `contract`/`constraints` for the DB-level UNIQUE;
a new least-privilege `dbt_app` Postgres role (read `staging`, read+write `silver` only) created
via an Alembic migration following migration 0011's exact `CREATE ROLE ... LOGIN` shape; and a
dedicated `dbt` Kubernetes ServiceAccount + Vault Kubernetes-auth role/policy mirroring
`csv-processor`'s existing pattern exactly.

This is a data platform, not a web app — "tiers" below map to this project's own established
layers (Airflow orchestration, ETL/Transform compute pods, PostgreSQL schemas, object storage,
secrets).

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Bronze ingestion (parse/normalize/stage) | ETL Compute (Python KPO, `dataplat`) | PostgreSQL (`staging`/bronze schema) | Unchanged, Phases 1-8; `csv_processor` owns parsing, never dbt |

| Silver-to-gold publish | ETL Compute (Python `MergePublisher`) | PostgreSQL (`normalized`/gold schema) | D-02/D-10: unchanged mechanism, single META-03 transaction, `INSERT ... ON CONFLICT` |

## Architecture Patterns

### System Architecture Diagram

```
MinIO (raw/, immutable)
   │
   ▼
S3KeySensor + list_matched_keys + integrity_gate  (Airflow, existing, unchanged)
   │
   ▼
KPO "discover"  (dataplat discover)  — schema/dialect detect, meta.files/batches
   │
   ▼
KPO "stage" ── formerly half of "ingest" ── D-04's new split
   │  Python: parse/validate/normalize/hash, COPY into a scratch UNLOGGED
   │  buffer, then INSERT ... INTO the new stable/cumulative bronze table
   │  (D-01) — the durable staging/bronze schema, append-only
   ▼
PostgreSQL  staging.<dataset>  (NEW: durable, LOGGED, cumulative — not the
             old per-run UNLOGGED throwaway table, which now survives only
             as a transient COPY buffer feeding this table)
   │
   ▼
KPO "dbt build"  ── NEW, this phase ──
   │  dbt-postgres: is_incremental() cursor on _run_id/_batch_id (never
   │  event_ts, D-06) → business-key-primary dedup (window function) →
   │  hash-secondary dedup → event_ts-ordered late-arrival resolution →
   │  delete+insert into silver → post-hook writes meta.dedup_audit,
   │  same transaction
   ▼
PostgreSQL  silver.customers / silver.orders  (NEW schema, dbt_app-owned,
             DB-level UNIQUE/PK constraint via dbt contract, D-14)
   │
   ▼
KPO "publish" ── formerly the other half of "ingest" ── unchanged internals
   │  Python MergePublisher/OrdersMergePublisher: pg_advisory_xact_lock +
   │  INSERT ... ON CONFLICT, reading FROM silver instead of staging,
   │  inside the single META-03 transaction (watermark + run-status)
   ▼
PostgreSQL  normalized.customers / normalized.orders  (gold, unchanged)
   │
   ▼
meta.v_customers_lineage  (extended, D-12, bridges the new dbt hop)
```

A reader can trace one row end to end: raw file → `discover`'s `meta.files` row → `stage`'s
bronze insert (`_run_id`) → dbt's `is_incremental()` filter picks it up → dbt's dedup/ordering
logic resolves its final state in `silver` → `meta.dedup_audit` records why any competing rows
were dropped → `publish`'s `MergePublisher` reads silver and writes gold → the lineage view
resolves the whole chain in one query.

### Pattern 1: Non-event-time incremental cursor (D-06's required shape)

**What:** `is_incremental()` combined with a `WHERE` clause keyed on a monotonic ingestion-side
marker, never `event_ts`.
**When to use:** Every silver model — this is the mechanism that makes D-05 (watermark-driven,
self-healing) and D-06 (never filter on event time) both true simultaneously.
**Example** `[CITED: docs.getdbt.com/docs/build/incremental-models]`:
```sql
{{ config(
    materialized='incremental',
    incremental_strategy='delete+insert',
    unique_key='customer_id',
    on_schema_change='fail'
) }}

with bronze as (
    select * from {{ source('bronze', 'customers') }}
    {% if is_incremental() %}
    -- D-06: keys off the monotonic _run_id load-order marker, NEVER
    -- event_ts. A late-arriving row with an old event_ts but a NEW
    -- _run_id is correctly picked up here; event_ts is used only below,
    -- to decide ordering AMONG rows already selected by this filter.
    where _run_id > (select coalesce(max(_run_id), 0) from {{ this }})
    {% endif %}
),

-- D-07 layer 1 (primary): business-key dedup within this incremental
-- batch. Postgres has no QUALIFY clause (unlike Snowflake/DuckDB) — the
-- window function must land in a CTE, filtered by an outer WHERE.
-- Mirrors merge.py's own DISTINCT ON / ORDER BY event_ts DESC precedent
-- for exactly the same structural reason (C1: an INSERT/DELETE+INSERT
-- source containing duplicate keys is undefined/incorrect behavior).
business_key_ranked as (
    select *,
           row_number() over (
               partition by customer_id
               order by event_ts desc, _source_row_number desc
           ) as rn
    from bronze
)

select * from business_key_ranked where rn = 1
-- D-07 layer 2 (secondary, exact-row-hash): a further filter/anti-join
-- against silver's own _record_hash history belongs here too — full
-- design is a planning-level task, not specified further by research.
```

### Pattern 2: Atomic audit write via post-hook (D-09)

**What:** `post-hook` SQL runs inside the same transaction as the model's own DML by default on
Postgres — no special config needed for this to be atomic with the silver write.
**When to use:** Writing `meta.dedup_audit` as a side effect of the incremental model run.
**Example** `[CITED: docs.getdbt.com/reference/resource-configs/pre-hook-post-hook]`:
```sql
{{ config(
    ...,
    post_hook="
      insert into meta.dedup_audit
        (dbt_invocation_id, model_name, min_run_id, max_run_id,
         records_received, records_accepted, records_deduplicated, run_at)
      select '{{ invocation_id }}', '{{ this.identifier }}',
             (select min(_run_id) from {{ source('bronze','customers') }}),
             (select max(_run_id) from {{ source('bronze','customers') }}),
             ...
    "
) }}
```
Only use `post_hook={"sql": "...", "transaction": False}` for statements that must run *outside*
the transaction (e.g. `VACUUM`) — never for the audit insert, which must stay inside.
**Schema-design tension this surfaces (flag for the planner, not resolved here):** the existing
`meta.dedup_audit` sketch (ARCHITECTURE.md line 238: `run_id, strategy, keys, records_*`) assumes
one row per bronze `meta.ingestion_runs.run_id` — a 1:1 assumption from Phase 9's original,
now-superseded design. Under D-05's watermark-driven dbt batching, **one dbt invocation can span
multiple bronze runs** (if dbt lags, or several files land before its next execution). The
migration for `meta.dedup_audit` needs an explicit column decision: a `dbt_invocation_id` (dbt's
own UUID, via the `invocation_id` Jinja variable) plus a covered `min_run_id`/`max_run_id` range,
**not** a single `run_id` foreign key.

### Pattern 3: DB-level constraint via native dbt contract (D-14)

**What:** `contract: enforced: true` + `constraints:` on the model's `schema.yml` entry.
**When to use:** Both silver models, to get the same structural UNIQUE/PK guarantee gold already
has (migration 0006 precedent).
**Example** `[CITED: docs.getdbt.com/reference/resource-properties/constraints]`:
```yaml
models:
  - name: silver_customers
    config:
      contract: {enforced: true}
      on_schema_change: fail
    columns:
      - name: customer_id
        data_type: integer
        constraints:
          - type: not_null
          - type: unique
```
Postgres is explicitly the strictest adapter in dbt's own constraint support matrix — it
"generates real database-level DDL constraints that are actually enforced at insert/update time,"
unlike several cloud warehouses where the same config is documentation-only. **Why this matters
more than it might first appear:** `dbt build` runs a model's materialization and its schema tests
as separate steps — the model's data is already committed by the time a `unique`/`not_null` *test*
would report failure. A dbt schema-test failure is detected *after* bad data has landed; a real DB
constraint prevents the bad write from ever committing. This is the concrete mechanism behind
D-14's "if dbt's dedup logic has a bug, it should hit a hard constraint violation" — it only works
because the constraint is a genuine table constraint, not a dbt test.

### Pattern 4: Secret resolution across a second, independent image

**What:** This project's `vault://path#field` env-var scheme (`DATAPLAT_DB_DSN=vault://etl/
analytics-db#dsn`) is resolved by `dataplat.secrets.resolver.resolve_secret()` — code that lives
*inside* the `dataplat` Python package, invoked from `csv_processor.cli._build_common()`. A dbt
image, by design, should **not** bundle `dataplat` (that would recreate exactly the cross-image
coupling ADR-0004 avoids in the other direction — the dbt image would need rebuilding on every
unrelated `dataplat` change). But dbt's own `profiles.yml` only understands plain `env_var()`
reads — it has no concept of a `vault://` indirection, and dbt-postgres needs *five separate*
fields (host/port/user/password/dbname), not one DSN string `[CITED: docs.getdbt.com/docs/core/
connect-data-platform/postgres-setup]`.
**Recommended pattern, following this codebase's own established precedent:** `airflow/dags/
_common/integrity_gate.py`'s own docstring documents *exactly* this situation already solved
once — "the SQL shape below is duplicated from `get_or_create_dataset`/`create_file`... not
imported from it," because that Airflow-side code must never import `dataplat` (ADR-0004). Apply
the identical discipline in reverse: give the dbt image a small, standalone secret-resolution
entrypoint script (a few dozen lines using `hvac` directly, matching `resolve_secret()`'s
`vault://path#field` scheme) that runs *before* `dbt build` inside the pod's `cmds`, writing
`DBT_PG_HOST`/`DBT_PG_USER`/etc. into the process environment that `profiles.yml`'s `env_var()`
calls then read. This keeps the "never materialize a Kubernetes Secret" security property intact
without coupling the dbt image to the full `dataplat` package. Flagged in Open Questions as
needing a planning-level decision on exact shape (standalone script vs. a tiny shared library).

### Anti-Patterns to Avoid

- **`dbt-postgres`'s `merge` incremental strategy against silver:** compiles to literal PG
  `MERGE`; same BUG #18279 exposure this project's own `MergePublisher` already documents avoiding.
- **Custom `schema:` config on the silver models without overriding `generate_schema_name`:** dbt's
  default macro concatenates `{{ target.schema }}_{{ custom_schema }}` `[CITED: docs.getdbt.com/
  docs/build/custom-schemas]` — e.g., a `profiles.yml` `schema: silver` plus a model-level
  `+schema: silver` config would silently create `silver_silver`, not `silver`. Safe pattern: set
  `schema: silver` once in `profiles.yml`'s target and declare **no** per-model `schema:` override
  anywhere — every model lands directly in `silver` with zero concatenation.
- **Installing `dataplat`/`csv_processor` or `apache-airflow` into the dbt image**, or vice versa
  (dbt into the csv-processor or Airflow image) — three single-purpose images, matching this
  project's existing two-image discipline (ADR-0004), not two.
- **Relying on `merge`'s "single-writer in practice" as the sole safety argument.** `max_active_runs=1`
  + a `max_active_tis_per_dag=1` override on the `dbt build` task (mirroring `ingest`'s own D-12
  precedent) make single-writer true *today*, but nothing in dbt's own materialization takes a
  Postgres advisory lock the way `MergePublisher` explicitly does — `delete+insert` removes the
  dependency on that assumption holding forever, `merge` does not.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Cross-batch/cross-run dedup engine | A second Python `DeduplicationStage` (Phase 9's now-superseded plan) | dbt incremental model + `is_incremental()` cursor | D-07 explicitly retires the Python stage; building it anyway duplicates dbt's own job |

**Key insight:** every "don't hand-roll" item above has the same shape — this phase's temptation
is to solve a problem dbt (or this project's own existing precedent) already solves, with a new

## Common Pitfalls

### Pitfall 1: Backfill collides with the existing content-hash idempotency key

**What goes wrong:** D-16 asks for historical files to be reprocessed through stage→dbt→publish
via "Airflow's backfill capability." A naive re-trigger (classic `airflow dags backfill`, or just
letting the sensor re-discover files already on disk) does nothing — every historical file's
`idempotency_key` already has a `SUCCEEDED` row, and `claim_ingestion_run`'s claim guard is
`WHERE status IN ('PENDING','FAILED') OR (RUNNING AND lease expired)` — `SUCCEEDED` is
permanently excluded by design (this is *correct*, load-bearing behavior everywhere else in the
platform; it is specifically wrong only for this one deliberate re-processing scenario).
**Why it happens:** the idempotency-key formula (`dataset|content_sha256|config_hash|
processor_image|schema_version`) has no way to distinguish "already processed under the OLD
2-stage pipeline" from "already processed under the NEW 3-stage pipeline" — from the key's own
point of view, nothing has changed about the file, config, or schema.
**How to avoid:** this needs an explicit design decision, not a default. Two structurally sound
options, both compatible with `meta.ingestion_runs.replay_of_run_id` (a column that already exists
in the schema, per ARCHITECTURE.md's table, but has **no implemented replay mechanism or CLI verb
anywhere in the codebase today** — confirmed by grep):
1. Extend the idempotency-key formula with one more append-only term (matching `discovery.py`'s
   own documented convention: "the first four terms are never reordered or replaced" — this is the
   established pattern for evolving the formula) that changes when the pipeline's target shape
   changes (e.g. a `pipeline_version` or `target_schema_version` literal). Historical files then
   legitimately get a *new* `run_id`, claimable normally, and `replay_of_run_id` can point back at
   the original SUCCEEDED run for audit continuity — this is arguably what that column was reserved
   for.
2. A deliberate, explicit, out-of-band operation that resets specific historical rows' `status`
   back to a reclaimable state — riskier, since other code (lineage view joins, rejected-record
   resolution) may implicitly assume `SUCCEEDED` is permanent once reached.
**Warning signs:** a "backfill" DAG run that completes in seconds with zero rows staged, zero rows
in the new bronze table, and every task reporting `SKIPPED_DUPLICATE`.

### Pitfall 2: The claim/lease mechanism was designed for ONE pod's lifetime, not three

**What goes wrong:** `run_ingest`'s docstring is explicit: "claim-once... single-writer
publication... atomic status commit... inside the SAME transaction as the Publisher's own write"
— today, staging and publish happen inside *one* claimed run, *one* pod's lifetime, protected by a
5-minute lease refreshed by a heartbeat thread that only runs while that one pod is alive. D-04
splits this into three separate Airflow tasks (`stage` → `dbt build` → `publish`), potentially
three separate pods, potentially minutes apart (dbt's own build time, plus queueing on this
project's documented tight CPU budget). A heartbeat thread that only lives inside the `stage` pod
cannot keep a lease alive across a *later*, separate `publish` pod's execution.
**Why it happens:** D-02 explicitly decouples dbt's own task from "the Python claim/lease/
heartbeat mechanism that currently wraps `run_ingest`'s stage+publish as one unit" — but D-02 also
says "the claimed run still covers claim→stage→publish," which is only true if the claim/lease
*itself* is re-architected to span the new task boundary, not merely relocated.
**How to avoid:** this is a genuine open design question (see Open Questions below), not something
research should guess at — it needs to be an explicit planning decision: does the run stay
`RUNNING` (lease periodically refreshed by *each* task in the chain, not just staging) until
`publish` finalizes it, or does `stage`'s own claim get marked complete independently and
`publish` performs a second, separate claim/status transition? Either is workable; leaving it
implicit is not.
**Warning signs:** a `publish` task that fails with a lease-expired condition on any run whose
`dbt build` step took longer than 5 minutes, or (worse) a `publish` task that silently proceeds
without ever checking the lease, quietly reintroducing the exact "two writers, no lock" race
META-03 was built to eliminate.

### Pitfall 3: dbt's default schema-name concatenation

**What goes wrong:** a model or `dbt_project.yml` entry declaring `+schema: silver` on top of a
`profiles.yml` target `schema: silver` silently produces a table in `silver_silver`, not `silver`
— dbt's default `generate_schema_name` macro concatenates target schema + custom schema with an
underscore `[CITED: docs.getdbt.com/docs/build/custom-schemas]`.
**Why it happens:** the concatenation exists to protect *developers* sharing one target schema
during local development from colliding — a reasonable default for dbt's typical multi-developer
use case, wrong for this project's single deliberate schema name.
**How to avoid:** set `schema: silver` once, at the `profiles.yml` target level, and add **no**
per-model or per-folder `schema:` override anywhere in `dbt_project.yml`'s `models:` block.
**Warning signs:** `\dn` in `psql` shows an unexpected `silver_silver` (or similar) schema that
nothing in `dbt_project.yml` explicitly named.

### Pitfall 4: The persisted bronze table must be `LOGGED`, not `UNLOGGED`

**What goes wrong:** today's `staging.<dataset>__r<run_id>` table is deliberately `UNLOGGED` (no
WAL, faster COPY, acceptable because it's throwaway and replayable from raw). D-01's new stable,
cumulative bronze table is the opposite: durable history dbt depends on existing across restarts.
Reusing `StagingLoader`'s existing `CREATE UNLOGGED TABLE` pattern for the new durable table would
silently lose bronze history on any unclean PostgreSQL shutdown/crash.
**Why it happens:** `StagingLoader.load()` (`packages/dataplat/src/dataplat/load/staging.py`) is
the natural code to extend for "append into a durable table too," and it already knows how to
`CREATE UNLOGGED TABLE` — reusing that exact DDL statement for the new table is an easy, wrong,
one-line mistake.
**How to avoid:** the new stable bronze table must be created via a normal Alembic migration as a
plain (`LOGGED`) table, structurally distinct code from the scratch buffer's `CREATE UNLOGGED
TABLE`, even though both tables share nearly the same column shape.
**Warning signs:** none observable until a real crash — this is exactly the class of bug that is
invisible until the day it matters. Cover with an explicit migration-level assertion/test
(`\d+ staging.customers` shows `Persistence: permanent`, not `unlogged`), not just code review.

### Pitfall 5: dbt `build`'s test step does not block a bad model write

**What goes wrong:** `dbt build` runs a model's materialization, then its schema tests, as
separate steps. If the model itself succeeds but a `unique`/`not_null` test on it fails, the
model's (possibly bad) data has *already committed* — the test failure is reported, but does not
roll back what was just written.
**Why it happens:** this is standard, documented dbt behavior, not a bug — dbt tests are a
reporting/CI-gating mechanism, not a transactional guard.
**How to avoid:** exactly why D-14's real DB-level `UNIQUE`/PK constraint (Pattern 3 above) is
load-bearing, not redundant with dbt's own `unique` test — the constraint prevents the bad write
from ever committing; the test alone would only ever report it after the fact.
**Warning signs:** relying on `dbt build`'s exit code alone as the platform's dedup correctness
guarantee, with no DB-level constraint backing it.

## Open Questions

1. **How does the claim/lease/heartbeat mechanism span three Airflow tasks instead of one?**
   - What we know: `run_ingest` currently claims once and holds a 5-minute heartbeated lease for
     exactly one pod's lifetime, ending at `finalize_publication` inside the same transaction as
     the `Publisher`'s write (verified by direct reading of `pipeline/run.py`). D-04 splits stage
     and publish into separate Airflow tasks with `dbt build` in between.
   - What's unclear: whether the SAME `run_id`/lease should stay open (refreshed by a mechanism
     that outlives the `stage` pod) until `publish` finalizes it, or whether staging should
     complete its own claim independently and `publish` performs a second, separate claim/status
     transition against the same conceptual "run."
   - Recommendation: this is a plan-level architectural decision, not something research should
     guess at — it directly affects `meta.ingestion_runs`' state machine (is there a new `STAGED`
     status between `RUNNING` and `SUCCEEDED`? does `run_stages` — already designed per
     ARCHITECTURE.md's "Correctness phase" table — get built now instead of Phase 9?). Flag this
     as the first thing to resolve in planning; almost everything else in the DAG-task split
     depends on the answer.

2. **What exactly resolves the historical-file backfill's idempotency-key collision (Pitfall 1)?**
   - What we know: the mechanism must not be a silent, implicit re-run; `claim_ingestion_run`'s
     existing guard is correct behavior everywhere else and should not be weakened generally.
   - What's unclear: whether extending the idempotency-key formula (Option 1 in Pitfall 1) or an
     explicit reset/replay operation (Option 2) is the right call — and whether `replay_of_run_id`
     was actually intended for this exact scenario or for a different one (e.g. a manual
     single-file reprocess-after-correction case, per README §62 Replayability).
   - Recommendation: resolve before writing the backfill task's plan — this affects whether D-16's
     backfill is a normal DAG re-trigger (if Option 1) or a one-off scripted operation (if Option 2).

3. **Exact shape of the dbt-image secret resolver (Architecture Pattern 4).**
   - What we know: dbt's `profiles.yml` needs plain env vars (five separate fields, no DSN), and
     this project's `vault://` scheme is currently `dataplat`-internal code.
   - What's unclear: whether to write a genuinely standalone script (most consistent with the
     `integrity_gate.py` precedent) or factor `resolve_secret()`'s core logic into a tiny,
     independently-installable module both images can depend on without full `dataplat` coupling.
   - Recommendation: standalone script, per the existing precedent — but this is cheap enough to
     decide at plan-writing time rather than needing further research.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-------------------|
| V2 Authentication | Yes | Vault Kubernetes auth, dedicated `dbt` ServiceAccount + Vault role, mirroring `csv-processor`'s existing pattern — never a shared credential, never a master token |
| V3 Session Management | No | Not applicable — no user sessions in this pipeline |
| V4 Access Control | Yes | New `dbt_app` Postgres role: `USAGE`+`SELECT` on `staging` only, `USAGE`+`CREATE` (owner) on `silver` only — verified never granted `normalized`/`meta` write access, matching D-08's explicit constraint |
| V5 Input Validation | Yes (indirect) | dbt SQL is static, committed, Jinja-templated from model files — not built from runtime/CSV row content. | V6 Cryptography | No (indirect) | dbt itself performs no cryptographic operations; credential delivery reuses the existing hvac/Vault Kubernetes-auth mechanism, never hand-rolled |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|-----------------------|
| Over-granted `dbt_app` role (e.g. accidentally granted write on `normalized`) | Elevation of Privilege | Migration-scoped, explicit `GRANT`/`REVOKE` pairs (Code Examples above); a negative test proving `dbt_app` is denied write access to `normalized.*`, mirroring this project's existing SEC-12 negative-test convention |
| Credential materialized as a Kubernetes Secret for dbt (via Agent Injector/CSI, instead of direct SA-token `hvac` login) | Information Disclosure | Reject Agent Injector/CSI for this workload (Don't Hand-Roll table) — use the same direct-login pattern `csv-processor` already uses |
| `dbt build`'s spurious-failure risk under a violated single-writer assumption (Anti-Patterns) | Denial of Service (of the pipeline, not data corruption — BUG #18279 raises a loud unique-violation, it does not silently corrupt) | `delete+insert` instead of `merge`, plus `max_active_tis_per_dag=1` on the dbt task as defense-in-depth |
| A future `dbt build` invoked manually (out-of-band, bypassing Airflow's concurrency guards) racing a scheduled run | Tampering (of silver, not gold — gold stays protected by its own advisory lock regardless) | Document that `dbt build` must only ever be invoked via the KPO task in this DAG, never manually against a live cluster's silver schema — an explicit runbook note, not enforceable purely in code within this phase's scope |
