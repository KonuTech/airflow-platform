# Phase 08.1 Plan 05: Control-Plane Metadata — dedup audit trail + two-phase claim Summary

**Two Alembic migrations (0024, 0025) completing this phase's control-plane schema: `meta.dedup_audit`/`meta.dedup_decisions` (dbt's own INSERT-only dedup audit trail, keyed on dbt's `invocation_id` + a `min_run_id`/`max_run_id` range instead of a single `run_id` FK) and `meta.run_stages` (D-17's `UNIQUE(run_id, stage_name)` two-phase claim table, `etl_app`-only, zero grant to `dbt_app`).**

## Performance

- **Duration:** ~20 min
- **Tasks:** 2 completed (Task 2 was TDD: RED → GREEN)

## Accomplishments

- `meta.dedup_audit` / `meta.dedup_decisions` created (migration 0024): the per-dbt-invocation dedup summary and per-dropped-row detail tables plan 08.1-08's dbt post-hook will write into, with `dbt_app` granted `SELECT, INSERT` only (never `UPDATE`/`DELETE`) — proven live by connecting as `dbt_app` via `SET ROLE` and asserting the INSERT succeeds while both an `UPDATE` and a `DELETE` raise `psycopg.errors.InsufficientPrivilege`.
- `meta.run_stages` created (migration 0025) via TDD: both tests (`UNIQUE(run_id, stage_name)` enforcement, `dbt_app` zero-grant) were written and confirmed failing (`psycopg.errors.UndefinedTable` / empty grant set) before the migration existed, then confirmed passing once it did.
- Fixed a real gap discovered while wiring `dbt_app`'s access: `dbt_app` had `USAGE` on `staging`/`silver` (migration 0021) but never on `meta` — without it, migration 0024's table grants would have been inert (the exact class of bug migration 0008's own docstring documents for `etl_app`/`normalized`). Added `GRANT USAGE ON SCHEMA meta TO dbt_app`, scoped to only the schema-level access this migration's new tables need.
- Full `tests/integration/test_migrations.py` suite (15 tests) passes; `alembic upgrade head` → `downgrade 0023` → `upgrade head` again verified to succeed cleanly against a throwaway PostgreSQL 18 container.

## Decisions Made

- `meta.dedup_audit`'s row identity is dbt's own `invocation_id` (Text, a UUID string) plus a nullable `min_run_id`/`max_run_id` range — **not** a `ForeignKey` to `meta.ingestion_runs`, since dbt's own transaction writes these and the referenced run rows may not exist yet from dbt's point of view at write time. This is the plan's own stated correction to ARCHITECTURE.md's original 1:1-per-run sketch (RESEARCH.md Pattern 2).
- `meta.dedup_decisions.dedup_audit_id` **is** a real `ForeignKey` back to `meta.dedup_audit` (safe — same dbt transaction writes both rows).
- `dbt_app` is INSERT-only on both dedup tables (T-08.1-10 mitigation): a post-hook only ever appends, never revises history. `etl_app`/`grafana_reader` get `SELECT` for reconciliation/dashboards.
- `meta.run_stages` grants **nothing** to `dbt_app` (D-02): the Python `stage_ingest`/`publish_ingest` claim/heartbeat mechanism (plan 08.1-10) stays fully decoupled from dbt's own task.
- `stage_name`/`status`/`reason` stay plain `Text`, app-validated — never native Postgres ENUMs — matching this repo's established `rule_type`/`outcome` convention (migrations 0009/0014).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] `dbt_app` had no `USAGE` on schema `meta`**
- **Found during:** Task 1 (writing the `dbt_app` grants for `meta.dedup_audit`/`meta.dedup_decisions`)
- **Issue:** Migration 0021 granted `dbt_app` `USAGE` on `staging`/`silver` only. Without schema-level `USAGE` on `meta`, migration 0024's `GRANT SELECT, INSERT ON meta.dedup_audit, meta.dedup_decisions TO dbt_app` would be inert — every statement `dbt_app` issued against those tables would fail with `permission denied for schema meta`, regardless of the table-level grant rows existing. This is the same class of bug migration 0008's own docstring documents for `etl_app`/`normalized`.
- **Fix:** Added `GRANT USAGE ON SCHEMA meta TO dbt_app` in migration 0024's `upgrade()`, with a corresponding `REVOKE` in `downgrade()`.
- **Files modified:** `migrations/versions/0024_meta_dedup_audit_decisions.py`
- **Verification:** `test_dbt_app_can_insert_dedup_audit_but_not_update_or_delete`'s live `SET ROLE dbt_app` + `INSERT` would otherwise fail with `InsufficientPrivilege` on the schema itself before ever reaching the table-level check; it now succeeds.
- **Committed in:** `faed503` (Task 1 commit)

**2. [Rule 1 - Bug] `tests/integration/test_migrations.py` was missing `pytestmark = pytest.mark.integration`**
- **Found during:** Task 1, running the plan's own literal `<verify>` command
- **Issue:** Every sibling module in `tests/integration/` (`test_backfill_resolution.py`, `test_volume_anomaly.py`, `test_metrics_otlp.py`, etc.) carries `pytestmark = pytest.mark.integration` at module scope. `test_migrations.py` never did, despite needing the same throwaway-Docker-container fixtures. Running `pytest tests/integration/test_migrations.py -k dedup_audit -m integration` (this plan's exact verify command) silently selected zero tests instead of the intended one, because `-m integration` filtered out every test in the file.
- **Fix:** Added the module-level `pytestmark = pytest.mark.integration`, matching the established convention.
- **Files modified:** `tests/integration/test_migrations.py`
- **Verification:** `pytest tests/integration/test_migrations.py -k dedup_audit -m integration -q` now selects and passes 1 test (previously: 0 selected). `make test-integration`'s own invocation (no `-m` filter) is unaffected either way.
- **Committed in:** `faed503` (Task 1 commit)

**3. [Rule 1 - Bug] `test_grafana_reader_role_exists_and_is_select_only`'s expected object set was stale**
- **Found during:** Task 1, running the full `test_migrations.py` suite as a broader sanity check beyond the plan's scoped `-k dedup_audit` verify command
- **Issue:** Migration 0024 grants `grafana_reader` `SELECT` on `meta.dedup_audit`/`meta.dedup_decisions` (per the plan's own action text), but the pre-existing test's `expected_objects` set didn't include them, so the test failed once migration 0024 landed.
- **Fix:** Added `("meta", "dedup_audit")`/`("meta", "dedup_decisions")` to `expected_objects`.
- **Files modified:** `tests/integration/test_migrations.py`
- **Verification:** Full suite re-run, test passes.
- **Committed in:** `faed503` (Task 1 commit)

**4. [Rule 1 - Bug] `EXPECTED_TABLES`/`GRANTED_TABLES` and `test_dbt_app_role_is_scoped_correctly`'s forbidden-grants query needed updating for the new tables**
- **Found during:** Task 1, same broader sanity pass
- **Issue:** `GRANTED_TABLES` was previously derived as `sorted(EXPECTED_TABLES)` and used by `test_etl_app_grants` to assert `etl_app` holds exactly `SELECT, INSERT, UPDATE` on every table in the set. Adding `meta.dedup_audit`/`meta.dedup_decisions` to `EXPECTED_TABLES` (needed so `test_upgrade_head_creates_the_slice_schema` still matches the real table set) would have wrongly required `etl_app` to hold `INSERT`/`UPDATE` there too, when the plan deliberately makes those tables `SELECT`-only for `etl_app`. Separately, `test_dbt_app_role_is_scoped_correctly`'s negative assertion (`dbt_app` must hold zero grants on `meta`) needed to exclude the two tables `dbt_app` is now legitimately granted on.
- **Fix:** Decoupled `GRANTED_TABLES` from `EXPECTED_TABLES` (`EXPECTED_TABLES - {dedup_audit, dedup_decisions}`), and narrowed the forbidden-grants query to exclude `dedup_audit`/`dedup_decisions` by name.
- **Files modified:** `tests/integration/test_migrations.py`
- **Verification:** Full suite re-run, both tests pass; `meta.run_stages` (added in Task 2) is *not* excluded from `GRANTED_TABLES`, since `etl_app` does hold the full `SELECT, INSERT, UPDATE` set there.
- **Committed in:** `faed503` (Task 1 commit)
