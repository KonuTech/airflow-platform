The freshness HAVING query — reuse this EXACT SQL text verbatim from Plan 07-01's
tests/integration/test_freshness_query.py (read that file first; do not re-derive independently,
or the alert rule and the already-proven-correct test will drift):
    SELECT d.dataset_id, d.dataset_name, ...
      FROM meta.datasets d
      LEFT JOIN meta.files f ON f.dataset_id = d.dataset_id
      LEFT JOIN meta.ingestion_runs r ON r.dataset_id = d.dataset_id
     WHERE d.expected_frequency IS NOT NULL
     GROUP BY d.dataset_id, d.dataset_name, d.expected_frequency, d.freshness_warn_after,
              d.freshness_fail_after, d.created_at
    HAVING now() - COALESCE(MAX(f.discovered_at), d.created_at)
           > d.expected_frequency + COALESCE(d.freshness_warn_after, interval '0')

The 8 named-metric source columns (all from meta.ingestion_runs unless noted; D-03's own mapping,
verified against migration 0004's real column list): files_processed/files_failed derive from
COUNT(*) grouped by status ('SUCCEEDED'/'FAILED') where file_id IS NOT NULL; rows_processed =
SUM(rows_loaded); rows_invalid = SUM(rows_invalid); rows_deduplicated = SUM(rows_deduplicated);
processing_duration = an aggregate (avg or percentile) of duration_ms; validation_failures is
DOCUMENTED as the same SUM(rows_invalid) signal until Phase 8's meta.validation_results exists (no
finer-grained validation-failure table exists yet — do not invent one here); data_freshness is the
freshness HAVING query above, rendered as a table (which datasets are currently stale), not a
time series.

The 3 live-gauge PromQL sources (Prometheus datasource, D-03; `runs_started`/`runs_finished` from
plan 07-05, `rows_rejected`/`rows_kept` from plan 07-02 — all four already carry
dataset/stage/status labels, nothing wider — and ALL FOUR are only visible to Prometheus once this
plan's own Task 1 `additionalServiceMonitors` entry exists):
    in-flight runs:    sum(runs_started) - sum(runs_finished)
    recent failure rate: sum(rate(runs_finished{status="failed"}[5m])) / sum(rate(runs_finished[5m]))
    row-level reject rate: sum(rate(rows_rejected[5m])) / (sum(rate(rows_rejected[5m])) + sum(rate(rows_kept[5m])))

Grafana provisioning shape (RESEARCH.md Pattern 4 — native `alerting: {}` values key, NOT the
sidecar ConfigMap-watcher mechanism; single-`$` env var interpolation ONLY, per RESEARCH.md
Pitfall 5 — `${VAR}` double-expands `$`):
    grafana:
      envFromSecret: grafana-alert-webhook   # the exact Secret name plan 07-06 created
      additionalDataSources:
        - name: analytics-postgres
          type: postgres
          url: analytics-db-rw.data.svc.cluster.local:5432
          user: grafana_reader
          secureJsonData:
            password: $GRAFANA_DB_PASSWORD
      alerting:
        contactpoints.yaml: {apiVersion: 1, contactPoints: [{name: platform-webhook, receivers: [{type: webhook, settings: {url: $GRAFANA_ALERT_WEBHOOK_URL}}]}]}
