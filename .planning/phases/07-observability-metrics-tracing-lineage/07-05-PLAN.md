<objective>
Complete the pod-side half of OBS-10: `dataplat.cli.main()` extracts an incoming `TRACEPARENT` env
var into the active OTel context before anything else runs, `run_ingest()` opens its own named
span (a genuine child of that extracted context) and captures the resulting `trace_id`/`span_id`,
and `claim_ingestion_run()` persists both onto the exact `meta.ingestion_runs` row Airflow's own
task span initiated — the columns Phase 3 already modeled and Phase 4 always left `NULL`. The same
function also gets the ONLY two OBS-08 live-gauge signals Plan 07-02 could not cover on its own
(D-03's "runs currently in-flight" and "recent failure rate" — the third, "row-level reject rate,"
was already fully covered by Plan 07-02's `dataset`/`stage`/`status`-labeled `rows_rejected`/
`rows_kept` counters): `run_ingest` is the one place in this codebase that knows a run has been
successfully claimed and the one place that can guarantee an emission on every exit path,
including an uncaught run-fatal exception.

Purpose: after this plan, "the context crossing the pod boundary" (OBS-10's literal requirement)
is not just a pod-spec env var (Plan 07-04's half) but a provable database fact: the SAME trace_id
Airflow's span carries shows up, unmodified, on the metadata row the processor itself claimed and
published — with a real, distinct child span_id recorded alongside it. The publish transaction
itself additionally gets its own nested `pipeline.publish` child span — the literal "→ PostgreSQL"
segment of OBS-10's Airflow task → task pod → processor → PostgreSQL trace, closing the one hop
RESEARCH.md's Standard Stack section flagged as still needing a manual span. And Grafana's live
gauges (Plan 07-07) have real, bounded-cardinality counters to derive "in-flight"
(`sum(runs_started) - sum(runs_finished)`) and "failure rate" (`runs_finished{status="failed"}`
over the total) from, with no new instrument-type complexity (both stay ordinary monotonic counters
— an up/down gauge is deliberately NOT introduced here). Plan 07-08 proves the trace half live,
against a real cluster; this plan proves both mechanisms correct against testcontainers.
Output: `cli.py` extracts context and configures both backends once; `run_ingest()`/`postgres.py`/
`repository.py` thread `trace_id`/`span_id` through the same single `UPDATE` `claim_ingestion_run`
already issues; `run_ingest()` emits `runs_started`/`runs_finished`; the publish transaction gets
its own nested `pipeline.publish` span.
</objective>
