The `config.secrets` block to add (verbatim, both values files -- Task 1's own copy target):
```yaml
config:
  secrets:
    backend: airflow.providers.hashicorp.secrets.vault.VaultBackend
    backend_kwargs: >-
      {"url": "http://vault.vault.svc.cluster.local:8200",
       "auth_type": "kubernetes",
       "kubernetes_role": "airflow",
       "mount_point": "airflow",
       "connections_path": "connections",
       "variables_path": null,
       "config_path": null,
       "kv_engine_version": 2}
```
- `variables_path: null` is load-bearing, not decorative: `airflow/dags/_common/kpo.py`'s `common_kpo_kwargs()` calls `Variable.get("csv_processor_image")` at DAG-PARSE time (inside the `@dag`-decorated function body). Routing Variable lookups through Vault would put a network call on the DAG processor's parse-time critical path for a value this phase never intends to move. Set it explicitly to `null`, do not omit it.
- `helm/values/local/airflow.yaml` and `helm/values/ci/airflow.yaml` currently have NO `config:` top-level key (confirmed by a full read this session) -- this task creates it. The chart's `config:` values convert to `AIRFLOW__<SECTION>__<KEY>` env vars on every Airflow component pod automatically; no per-component wiring is needed the way `extraVolumes`/`env` needed four separate insertion points in plan 04-02 -- `config:` is global.
- The THREE existing `env: - name: AIRFLOW_CONN_MINIO_DEFAULT` / `valueFrom: secretKeyRef: {name: airflow-minio-connection, key: AIRFLOW_CONN_MINIO_DEFAULT}` blocks, IDENTICAL in shape, live at: `triggerer.env` (local file, ~line 109), `scheduler.env` (local file, ~line 190), `workers.kubernetes.env` (local file, ~line 272) -- and the identical three in `helm/values/ci/airflow.yaml`. Six occurrences total across both files. Each must be removed only after this plan's own proof passes (D-01) -- not before, and not left half-removed.
- Five candidate ServiceAccounts exist live in namespace `airflow`: `airflow-api-server`, `airflow-scheduler`, `airflow-dag-processor`, `airflow-triggerer`, `airflow-worker`. Plan 05-01's `vault-bootstrap.py` bound the `airflow` role to `airflow-api-server` as a documented best guess (Airflow 3's "API server is the sole metadata-DB access point for tasks and workers" principle, extended by inference to secrets-backend lookups -- NOT independently confirmed). This project's own live DAG (`csv_ingest_customers.py`) uses a `deferrable=True` `S3KeySensor` against `aws_conn_id="minio_default"` -- exactly the ambiguous case (trigger-side connection resolution inside the triggerer process, which may or may not proxy through the API server).
- The persistent Vault audit log is readable via `kubectl exec -i -n vault vault-0 -- tail -n <N> /vault/audit/audit.log` (the already-permitted `exec -i` pattern) -- use this DIRECTLY as a one-off diagnostic command during this task, before `scripts/vault-audit-tail.py` exists (that is plan 05-04's own deliverable). Each audit entry's `auth.metadata.service_account_name` and `auth.metadata.service_account_namespace` fields (Vault's Kubernetes-auth login response metadata) name the identity that attempted the login -- read these directly, do not guess from the pod name alone.
