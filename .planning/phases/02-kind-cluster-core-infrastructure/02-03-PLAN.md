<objective>
Add the two physically separate PostgreSQL clusters to the proven bootstrap path: PostgreSQL 17
dedicated exclusively to Airflow metadata, PostgreSQL 18 for analytical workloads, each a distinct
CloudNativePG `Cluster` resource on its own worker node with its own storage.

Purpose: README §4's requirement is that the separation stays visible even inside one cluster.
Nominal separation — two databases in one server, or two `Cluster` resources the scheduler may
co-locate on one node with one local-path volume — satisfies the letter and loses the point. This
plan makes the separation physical and then proves it.

Output: the CloudNativePG operator, two `Cluster` CRs in both values profiles, three ordered
bootstrap stages with the readiness waits Helm cannot supply, and the live-cluster test that
asserts both server versions and their disjointness.
</objective>

<user_story>
**As a** data engineer,
**I want to** point Airflow at one PostgreSQL and my analytical loads at a different one that
cannot possibly be the same server,
**so that** a runaway `COPY` into the warehouse can never take the orchestrator's metadata down
with it, and "which database is this row in?" always has one answer.
</user_story>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CNPG operator → `Cluster` CR | the operator holds cluster-admin-shaped rights over PostgreSQL instances and generates their credentials |
| test process → PostgreSQL `-rw` service | the e2e suite authenticates with credentials read from a cluster-local Secret |
| Airflow metadata database ↔ analytical database | README §4's boundary: neither may host the other's data |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-11 | Information Disclosure | PostgreSQL credentials | high | mitigate | CloudNativePG generates and stores both clusters' credentials; no values file, manifest or script contains one, and the e2e tests read them from the live Secret at run time (D-14) |
| T-02-12 | Elevation of Privilege | analytical application role | medium | mitigate | `postInitApplicationSQL` creates `etl_app` with `LOGIN` and explicit grants only — never a superuser, never an owner (D-15) |
| T-02-13 | Tampering | a `Cluster` CR applied before the admission webhook serves | high | mitigate | The operator stage waits for both CRD establishment and the operator Deployment becoming Available; the measured failure mode is a webhook dial refusal that leaves a half-created cluster |
| T-02-14 | Denial of Service | co-located databases on one node | medium | mitigate | Explicit `nodeSelector` on each `Cluster` and a live test asserting the two primaries sit on different nodes; local-path PVs are node-bound, so co-location is also a storage-contention risk |
| T-02-15 | Denial of Service | unbounded PostgreSQL resource use | high | mitigate | Full `cluster.resources` requests and limits on both clusters in both profiles; the CI profile is additionally bounded by the D-12 sizing test in plan 02-08 |
</threat_model>
