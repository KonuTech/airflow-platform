<objective>
Add S3-compatible object storage to the proven bootstrap path: five buckets addressable as
`s3://bucket/key`, versioning on `raw`, a server-enforced deny on deleting anything in `raw` for
the application credential, and credentials that are generated into the cluster and never touch the
working tree.

Purpose: §5's claim is that MinIO can be replaced by AWS S3 without a code change, and §63's claim
is that the raw layer is append-only. Both are claims about the *client contract* and the *server
policy*, so both are proved through boto3 against a real deny statement — not through MinIO's own
CLI and not by a convention nobody enforces.

Output: the MinIO chart in both values profiles, the credential generator, the bootstrap stage, and
the live-cluster test including the negative delete case.
</objective>

<user_story>
**As a** data engineer,
**I want to** read and write my data lake as `s3://raw/...` with an ordinary S3 client, and be
physically unable to delete anything from `raw` with the credential my pipelines use,
**so that** the raw layer's immutability is a property of the platform rather than a rule people
remember, and pointing the same code at real AWS S3 is one environment variable.
</user_story>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| developer host → MinIO API | requests cross the ingress with a live credential |
| pipeline application credential → `raw` bucket | the §63 immutability boundary, enforced by the MinIO policy engine |
| credential generation → Kubernetes Secret | values exist between `/dev/urandom` and the API server and must never touch disk |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-16 | Information Disclosure | `scripts/minio-credentials.sh` | high | mitigate | Values are piped to `kubectl create secret` from stdin, never placed on a command line or written to the working tree; `ensure` never echoes; a clean `git status` after running is an acceptance criterion; gitleaks has been live since Phase 1 |
| T-02-17 | Tampering | objects in `s3://raw/` | high | mitigate | A single IAM document attached to the application credential denies `DeleteObject` and `DeleteObjectVersion` on `raw`, plus bucket versioning, so a corrected file is a new version rather than an overwrite. Enforcement lives below the application, per §63 |
| T-02-18 | Elevation of Privilege | admin credential reachable by the pipeline | medium | mitigate | Two-credential split: the application user is attached only to the `etl-app` policy; the admin credential is used by no workload and only by the operator and the e2e positive control. This is deliberately the shape Phase 5's Vault policies need |
| T-02-19 | Spoofing | unauthenticated access to buckets | medium | mitigate | Every bucket sets the anonymous access policy to none, so no bucket is publicly readable or writable |
| T-02-20 | Denial of Service | MinIO's stock resource defaults | high | mitigate | `mode: standalone`, `replicas: 1` and explicit requests and limits on the deployment and all three post-job containers; the stock defaults request 16Gi and 16 replicas and would make a kind node unschedulable |
| T-02-SC | Tampering | `pgsty/minio` and `quay.io/minio/mc` | high | mitigate | Both are knowingly-adopted unmaintained-upstream artifacts, version-pinned, with the risk acceptance recorded in ADR-0006 (plan 02-05); the boto3-only client contract keeps the escape hatch a values change |
</threat_model>
