<objective>
Add Airflow 3.3.0 to the proven bootstrap path, running against the PostgreSQL 17 metadata cluster
with its four components as four separate workloads and its UI answering through the ingress.

Purpose: this is the last component of the phase and the one the whole platform orchestrates with.
It is also the one place where two upstream contracts do not meet — the Airflow chart wants a Secret
with a key named `connection`, and CloudNativePG produces an eleven-key Secret with a different
shape — so this plan writes the single hand-written adapter of the phase and nothing else by hand.

Output: the Airflow chart in both values profiles with `postgresql.enabled: false`, the
metadata-connection adapter, the bootstrap stage, and the live test asserting the four workloads
with their correct kinds.
</objective>

    `scripts/airflow-metadata-secret.sh` with an `ensure` subcommand, idempotent in the same sense as
    `scripts/minio-credentials.sh ensure`.

    It creates three Secrets in namespace `airflow`:

    The derived metadata connection. Read Secret `airflow-db-app` from namespace **`data`** — a
    cross-namespace read, because D-13 places both `Cluster` CRs in `data` while the Airflow chart
    requires its metadata Secret in its own namespace. Note that this supersedes the phase
    research's architecture diagram, which drew `airflow-db` inside the `airflow` namespace; D-13 is
    the authority.

    State the trust model in the script header, because a cross-namespace secret read that nobody
    explains reads later like an accident. The principal is the **developer's own kubeconfig
    context**: this script runs host-side during `make cluster-up`, as the human who created the
    cluster, with the credentials `kind` wrote to their kubeconfig. It therefore needs no
    ServiceAccount, no Role and no RoleBinding, and this plan creates none — nothing inside the
    cluster is granted cross-namespace secret access, and no in-cluster workload can perform this
    read. Say so explicitly, and say what changes when it moves: Phase 5 replaces this derivation
    with Vault, and an in-cluster replacement (a Job, an operator, or a Vault sync) will need
    either a Role and RoleBinding in `data` naming a ServiceAccount in `airflow`, or a Vault policy
    plus a Kubernetes-auth role bound to `system:serviceaccount:airflow:<name>`. Neither exists
    yet, deliberately. Extract `username`, `password`, `host`, `port` and `dbname`, URL-encode the user
    and the password, assemble a PostgreSQL URI, and write it into Secret `airflow-metadata` under
    key `connection`. URL-encoding is not optional: CloudNativePG generates random passwords that
    can contain characters which break a URI, and the failure surfaces as an opaque migration-job
    error. Do not use the `-app` Secret's own `uri` key without re-encoding, and do not echo the
    assembled URI.

    The Fernet key, Secret `airflow-fernet-key`, and the API server secret key, Secret
    `airflow-api-secret-key`, each generated from a cryptographically secure source in the format
    Airflow expects. Both must be created once and left alone on subsequent runs: if these are left
    unmanaged the chart regenerates them on every `helm upgrade`, which orphans everything
    previously encrypted with the old Fernet key.

    Never write any of the three to the working tree, never pass a value on a command line, and
    never echo one. Take the key names the chart expects from the pinned chart's own helpers rather
    than from documentation.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| namespace `data` → namespace `airflow` | the adapter reads a CloudNativePG-generated Secret across a namespace boundary and writes a derived Secret. **Principal: the developer's kubeconfig context**, host-side during `cluster-up` — not an in-cluster identity. No ServiceAccount, Role or RoleBinding grants this read to any workload, and none is created here |
| host `:80` → Airflow API server | the UI and REST API are reachable from the developer's browser through the ingress |
| Airflow task workloads → metadata database | in Airflow 3 the API server is the sole metadata-DB access point for tasks and workers |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-23 | Information Disclosure | derived metadata connection Secret | high | mitigate | The adapter never echoes the assembled URI, never places it on a command line, and writes it only into namespace `airflow`; no connection string appears in a values file, a manifest or the working tree (D-14, §81) |
| T-02-23b | Elevation of Privilege | the `data` → `airflow` Secret read | medium | accept | The read is performed host-side by the developer's own kubeconfig during `cluster-up`, so it grants no in-cluster principal cross-namespace access and adds no RBAC surface. Accepted for a local, single-operator cluster; the script header records that a Phase 5 in-cluster replacement must add either a Role/RoleBinding in `data` or a Vault Kubernetes-auth role, neither of which this phase creates |
| T-02-24 | Cryptographic failure | `fernetKey` and `webserverSecretKey` | high | mitigate | Both are generated once from a secure source into named Secrets and are not regenerated by a `helm upgrade`; leaving them unmanaged makes the chart rotate them on every upgrade and orphan everything previously encrypted |
| T-02-25 | Spoofing | unauthenticated access to the Airflow UI | medium | accept | The chart's default auth manager is in force and the ingress is published on loopback only; full authentication hardening arrives with Phase 5's identity work. Accepted at ASVS L1 for a local-only platform |
| T-02-26 | Tampering | the bundled `bitnamilegacy` PostgreSQL subchart being re-enabled | high | mitigate | `postgresql.enabled: false` in both profiles, plus a live test asserting no pod runs a Bitnami legacy image |
| T-02-27 | Denial of Service | thirty empty `resources` keys in the chart | high | mitigate | The enumerated minimum key set is populated in both profiles; the CI profile is additionally bounded by the D-12 sizing test in plan 02-08 |
| T-02-28 | Elevation of Privilege | the KubernetesExecutor's Role and RoleBinding | medium | accept | The chart's own RBAC is scoped to the `airflow` namespace and is not widened here; the `etl` namespace exists but carries no workload until Phase 4, which is precisely what lets Phase 5's Vault role be written narrowly the first time (D-13) |
</threat_model>

## Planner note — a fourth divergence axis, argued rather than smuggled

D-06 caps the two values profiles at three divergence axes and states that any fourth needs an
argument. The executor is a fourth axis, and this plan introduces it deliberately: the CI runner is
4 CPU / 16 GB, KubernetesExecutor costs two pods and two multi-gigabyte image pulls per task, and
`values-ci.yaml` exists precisely because the full stack does not fit that runner. The argument is
written into both values files and is allowlisted by name in plan 02-08's profile test, so a fifth
axis still fails.
