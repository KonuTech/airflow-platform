`.planning/debug/ci-pipeline-ingestion-timeout.md` root cause (CONFIRMED, not speculative): `airflow-scheduler` and `airflow-dag-processor` pods crash-loop under real CI CPU contention because Airflow's own internal `scheduler_health_check_threshold` (default 30s) / `dag_file_processor_timeout` (default 50s) are tighter than the Kubernetes probe `timeoutSeconds` an earlier session already raised (20s→60s) — that earlier fix addressed probe-command latency, not DB-heartbeat staleness, a different mechanism.

Fix already merged (commit `a73282e`): raised scheduler/dagProcessor CPU requests+limits in `helm/values/ci/airflow.yaml` (scheduler 200m→400m/500m→1500m; dagProcessor 200m→300m/500m→1200m), and raised both Airflow-internal thresholds identically in both `helm/values/ci/airflow.yaml` and `helm/values/local/airflow.yaml` (behavioral config, not a permitted resource-sizing divergence axis).

**Live-verified result (direct `kubectl` restart-count evidence, via throwaway PR #13, now closed):**
- `airflow-scheduler-0`: genuinely improved — 1 restart (was "1+ restarts, not fully Ready" pre-fix), stays 2/2 Ready.
- `airflow-dag-processor`: **UNCHANGED** — still 5 restarts in ~9 minutes, statistically identical to the pre-fix baseline, still actively `CrashLoopBackOff` at snapshot time (`Back-off restarting failed container dag-processor`, 23s before capture). Its own logs show a completed parse cycle that processed `smoke_kubernetes_pod.py` in 0.09s with 0 errors but **0 DAGs registered** — consistent with the parse subprocess being killed mid-cycle before its DB commit, by the same restart the events show.
- Node CPU allocation: 2780m (92%) requests, up from 2480m (82%) pre-fix — matches the fix's own predicted +300m exactly, but leaves an even tighter margin. Limits show 7700m (256%) — severe overcommit risk if multiple pods burst simultaneously.
