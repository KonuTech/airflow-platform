<objective>
Close the loop plan 06-14 left open: `CsvSource.inspect()` now also resolves this file's schema
against the dataset's history. On first contact with a dataset, or when nothing has changed,
`SchemaRepository.sync()` is a no-op returning the current row. When the file's detected header adds a
genuinely new column, `classify_schema_change` (06-13) classifies it COMPATIBLE, `sync()` records a
new proposal row, and the file still loads using only its known/contract columns (D-01). When a
contract-declared column is missing or retyped, classification raises `IncompatibleSchemaError` before
`inspect()` returns — `StagingLoader.load()` never even opens a staging table for this file. When a
file's structure matches an OLDER (non-current) schema version, `resolve_by_hash` finds it — SCHEMA-06's
literal proof that a historical file processes under its historical schema, not the newest.

Purpose: SCHEMA-03/04/05/06 are architecturally designed to live on `Source.inspect()` — the
"5. schema inference + contract validation → CsvProfile" step 06-RESEARCH.md's own architecture
diagram names explicitly. This is the second, final integration step for the schema-versioning track
(06-12/06-13), sequenced after plan 06-14 because both touch `csv_processor/source.py`.
Output: `CsvProfile.schema_version_id`/`compatibility` populated for real; the whole D-01/D-02 behavior
proven against a live database, not just a pure-function unit test.
</objective>
