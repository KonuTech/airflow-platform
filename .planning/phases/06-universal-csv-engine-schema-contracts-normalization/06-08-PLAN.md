<objective>
Build CSV-11's compression and multi-part delivery support: `.gz` decompresses in a true single-pass
stream by wrapping `io.BufferedReader(response_body)` with `gzip.GzipFile(fileobj=...)` — zero
compromise, exactly like the existing uncompressed path. `.zip` cannot do this — 06-RESEARCH.md
verified live that `zipfile.ZipFile` requires a seekable stream because ZIP's central directory sits
at the archive's end — so per the user-confirmed D-22a resolution, `.zip`'s compressed archive bytes
are buffered into `io.BytesIO` first (bounded by the archive's compressed size, not the decompressed
CSV content, and never written to disk); the CSV content itself still streams out in small chunks once
open. Separately, group Spark-style multi-part deliveries (`part-00000`, `part-00001`, header in the
first part only) into one logical dataset at discovery time.

Purpose: one of Wave 2's five-detectors-plus-one plans (compression is grouped with the streaming
concern LOAD-07 shares). `customers` uses neither compression nor multi-part delivery, so — like
CSV-01's filename masks — this capability's evidence is its own corpus-fixture-driven tests (fixtures
`61_gzipped.csv.gz`, the new `71_zipped.csv.zip` from plan 06-01, and `62_multipart_split`), opt-in via
new config fields absent from `customers.yaml`.
Output: `open_compressed_stream` (the `.gz`/`.zip` dispatch), a `SourceConfig.multipart_pattern`
opt-in field, and a `discovery.py` grouping function proven against the multi-part corpus fixture.
</objective>

def open_text_stream(response_body: object, *, encoding: str, newline: str = "", errors: str = "strict") -> io.TextIOWrapper:
    buffered = io.BufferedReader(response_body)  # type: ignore[type-var]
    return io.TextIOWrapper(buffered, encoding=encoding, newline=newline, errors=errors)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Raw `.gz`/`.zip` bytes (from `raw` bucket) → `open_compressed_stream` | Untrusted content; the decompressor itself is the attack surface for a decompression bomb |
| Object-store listing → `group_multipart_units` | Object keys are attacker-influenceable (anyone who can upload); the regex pattern itself is operator-authored config |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-02 | Denial of Service | `.gz`/`.zip` decompression bomb (a small compressed file expanding to gigabytes) | mitigate | Task 2's `max_decompressed_bytes` ceiling, enforced incrementally during chunked reads — never after eager full decompression — fails with a named diagnostic once exceeded |
| T-06-28 | Denial of Service | An adversarial `.zip` archive engineered to be large before its central directory is even reachable | mitigate | D-21 already scopes `.zip` to exactly one CSV member per archive; Task 1's multi-member guard rejects anything else outright, bounding the buffered-in-memory size to what a legitimate single-CSV `.zip` archive should be |
| T-06-13 | Denial of Service | A crafted `multipart_pattern` regex causing catastrophic backtracking | mitigate | `multipart_pattern` is operator-authored config (not attacker-influenceable), and Task 3's example pattern uses only bounded, non-nested quantifiers — same discipline as the filename-mask compiler in plan 06-03 |
