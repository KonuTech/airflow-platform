## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] RESEARCH.md's literal Pattern-2 algorithm mis-detects `06_windows1250.csv`'s real generated bytes**
- **Found during:** Task 1, while empirically deriving `DEFAULT_MIN_CONFIDENCE` as the plan's Task 1 action explicitly required
- **Issue:** The plan's `<interfaces>` block algorithm (copied from `06-RESEARCH.md` Pattern 2) requires charset-normalizer's `.best()` pick to exactly match chardet's canonicalized guess. Against the actual bytes `tools.corpus.generators.generate_corpus` produces for `06_windows1250.csv`, charset-normalizer's own top pick is `iso8859-10` (tied with `iso8859-2` at identical chaos/coherence — an essentially arbitrary tie-break), not `cp1250`. The true encoding chaos-ranks third (`0.0900`) against a tied best of `0.0880`. Run literally, the algorithm reports `source="undetermined"` for a fixture whose own `expect:` block requires a successful `cp1250` detection at `encoding_confidence_max: 0.99`.
- **Fix:** Added `_best_corroborating_match`: when charset-normalizer's exact top pick disagrees with chardet, search its full (chaos-ascending) candidate list for a match within `_NEAR_TIE_CHAOS_EPSILON` (0.01) of the best chaos. Verified this does not over-accept using `39_utf8_invalid_sequences.csv`, whose spliced-garbage bytes also contain a `cp1250` candidate in charset-normalizer's list, but 0.091 behind the best — ~9x the epsilon — so it correctly stays a disagreement.
- **Files modified:** `packages/csv-processor/src/csv_processor/detect/encoding.py`, `tests/unit/detect/test_encoding.py`
- **Verification:** `test_windows1250_confidence_uses_chaos_not_chardets_raw_number`, `test_windows1250_true_encoding_is_not_charset_normalizers_own_top_pick`, and the generic parametrized assertion for `06_windows1250.csv` all pass; `test_undetermined_never_reports_a_specific_encoding` (fixture 39) confirms the epsilon did not over-widen.
- **Committed in:** `eeb6e58` (Task 1 commit)

**2. [Rule 1 - Bug] RESEARCH.md's literal algorithm falsely reports BOM-grade certainty for `40_utf16_no_bom.csv`**
- **Found during:** Task 1, same empirical-derivation step
- **Issue:** `40_utf16_no_bom.csv`'s real generated bytes are ~49.5% NUL. Both charset-normalizer (chaos exactly `0.0`) and chardet (raw confidence `0.95`) correctly and confidently identify `utf-16-le` — a genuinely correct read of the byte pattern. Run literally, the algorithm reports `confidence=1.0`, but the fixture's own `expect:` block requires `encoding_is_certain: false` and `encoding_confidence_max: 0.99`, since no byte-order mark exists to prove little-endian over big-endian.
- **Fix:** Added `_looks_like_unmarked_wide_encoding` (NUL-byte ratio > 30%) as a hard confidence ceiling (`_NO_BOM_CONFIDENCE_CEILING = 0.99`) applied after the chaos-derived confidence is computed. `06-RESEARCH.md` Pitfall 9 explicitly names this exact heuristic (STACK.md's documented ">30% NUL-byte-ratio heuristic") as required "defensive insurance regardless of what the primary detectors report" — this is that heuristic's first real implementation.
- **Files modified:** `packages/csv-processor/src/csv_processor/detect/encoding.py`, `tests/unit/detect/test_encoding.py`
- **Verification:** The generic parametrized assertion for `40_utf16_no_bom.csv` (`encoding_confidence_max`, `encoding_is_certain: false` → `confidence < 1.0` and `source != "bom"`) passes.
- **Committed in:** `eeb6e58` (Task 1 commit)
