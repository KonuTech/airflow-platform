<objective>
Build SCHEMA-03's hashing/versioning mechanism and SCHEMA-06's historical-resolution mechanism as pure
CRUD infrastructure mirroring `dataplat.config.hashing`/`dataplat.config.registry.ConfigRegistry`
almost line-for-line: `hash_schema` canonical-JSON-hashes a resolved column list exactly like
`hash_config` hashes a `DatasetConfig`; `SchemaRepository.sync()` implements the identical
versioned-upsert rule (hash matches current → no-op; hash differs → close the old row, insert
`version = max + 1`); `SchemaRepository.resolve_by_hash()` is D-16's mechanism — re-derive a file's
structure, hash it, and match it against `meta.schema_versions` history for that dataset, independent
of whether the dataset declares a filename mask.

Purpose: genuinely mechanical infrastructure, not novel domain logic — every design decision here was
already made when `ConfigRegistry` was built in Phase 3. This plan exists so Wave 2's schema-evolution
classification plan (06-13, a pure function with no DB dependency) has somewhere real to persist its
outcome, and so a later wiring plan can call one function to answer "does this dataset have a
`meta.schema_versions` row matching this exact structure, from any point in history."
Output: `hash_schema`, `SchemaRepository` (sync/get_by_hash/get_current), unit- and integration-tested
against a real migrated PostgreSQL from plan 06-01's migration 0009.
</objective>

CONFIG_HASH_VERSION: int = 1
def hash_config(config: DatasetConfig) -> tuple[str, int]:
    canonical = json.dumps(config.model_dump(mode="json"), sort_keys=True, separators=(",", ":"), ensure_ascii=False)
    config_hash = hashlib.sha256(canonical.encode("utf-8")).hexdigest()
    return config_hash, CONFIG_HASH_VERSION

# packages/dataplat/src/dataplat/config/registry.py::ConfigRegistry.sync() -- the EXACT versioned-

    - Reordering the SAME set of columns changes the hash (position is part of the schema's identity —
      unlike `hash_config`'s key-reordering tolerance, which is about YAML MAPPING key order, not
      column POSITION, which is semantically load-bearing for a CSV schema — document this distinction
      explicitly in this function's docstring, since it is the one place this recipe deliberately
      diverges from `hash_config`'s "reordering does not change the hash" property).
