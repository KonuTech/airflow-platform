<objective>
Wire the four normalizer stages built in Wave 2 into `StagingLoader.load()`'s real `stages=[...]`
list — the ONE place in this codebase they actually run against production data — and extend
`discovery.py`'s `idempotency_key` formula with the schema-version term its own standing code comment
already instructs this phase to add, plus filename-derived `business_date` population (D-11) for any
dataset that declares a mask.

Purpose: `dataplat/load/staging.py`'s `StagingLoader.load()` is the ONLY call site in this codebase
that constructs `run_streaming(ctx, stream.chunks(), stages=[RaggedRowGuard()])` — 06-PATTERNS.md's
own analysis found no other stage-list assembly point exists anywhere, and `dataplat/pipeline/engine.py`
itself needs zero changes (`run_streaming` already accepts any `Sequence[StreamingStage]` generically).
`customers` is the platform's only real dataset, and it needs exactly one of the four normalizers for
real — date normalization for `birth_date`/`event_ts` — so that is what this plan proves end-to-end
against a live database; the other three (numeric, boolean/null, unicode) are constructed correctly
whenever a dataset's contract calls for them (unicode NFC unconditionally, per D-15), even though
`customers` itself has no numeric/boolean columns to exercise them against in production. `birth_date`
is also `nullable: true` (plan 06-02 Task 3) — the platform's one real nullable typed column — so this
plan's stage ordering (each nullable column's `NullTokenNormalizer` runs BEFORE its type-specific
normalizer, never after) is not a cosmetic detail; it is what keeps an empty `birth_date` value from
being wrongly rejected as an invalid calendar date.
Output: `StagingLoader.load()` normalizes for real; `discovery.py`'s idempotency key and business-date
extraction are extended per Pitfall 5 and D-11, each with its own regression test.
</objective>

    Add a private method `_build_stages(self, ctx: PipelineContext) -> list[StreamingStage]` to
    `StagingLoader`. It always starts with `[RaggedRowGuard()]` (unchanged — the existing row-shape
    guard runs first, before any value-level normalization touches a row that is already
    structurally wrong). Then, for each `ColumnContract` in `ctx.config.columns`, at that column's
    positional index within `self._target_columns` (match by `ColumnContract.name ==
    self._target_columns[i]` — do not assume list order alignment without checking; raise a plain
    `ValueError` at staging-loader-construction time if a `ColumnContract` name has no corresponding
    `target_columns` entry, since that is a genuine contract/target-schema mismatch this phase's
    architecture has no other place to catch):

    FIRST, if that column is `nullable=True`, append its `NullTokenNormalizer` constructed from
    `ctx.config.normalization.null_tokens`/`null_sentinels[column.name]` (falling back to D-14's
    `[""]` default when `ctx.config.normalization` is `None`). This MUST be appended BEFORE the
    column's own type-specific normalizer below, never after — ordering, not just presence, is the
    load-bearing fix this plan makes: an empty/null-token value must already be `None` by the time
    `DateNormalizer`/`NumericNormalizer`/`BooleanNormalizer` sees it, so those normalizers'
    `None`-passthrough guards (plans 06-09/06-10/06-11) are actually reachable for the common case of
    a nullable typed column, rather than dead code that never sees a `None` input. `customers.yaml`'s
    `birth_date` (`type: date`, `nullable: true`) is the concrete, real case this ordering exists for.

    THEN, if `type == "date"` or `type == "timestamp"`, append a `DateNormalizer` constructed from
    that column's `format`/`fixed_width`-irrelevant fields plus `ctx.config.normalization`'s
    `two_digit_year_pivot`/`spreadsheet_epoch`/`timezone`/`ambiguous_time_policy` (all `None`/defaults
    when `ctx.config.normalization` is `None`, exactly `customers`' real case); if `type == "decimal"`
    or `type == "integer"`, append a `NumericNormalizer` constructed from `ctx.config.normalization`'s
    locale fields plus that column's `fixed_width`/`reject_scientific_notation`; if
    `type == "boolean"`, append a `BooleanNormalizer` constructed from
    `ctx.config.normalization.boolean_true_tokens`/`boolean_false_tokens`. (The nullable column's
    `NullTokenNormalizer` was already appended above, before this type-specific normalizer — do not
    append a second one here, and do not reorder these two steps.)

    Finally, append exactly ONE `UnicodeNormalizer()` — unconditionally, for every dataset, regardless
    of `ctx.config.normalization` being set at all (D-15: no per-dataset opt-out) — LAST in the list,
    after every other normalizer, per plan 06-11's documented ordering rule (other normalizers may
    still be matching against not-yet-NFC-normalized raw tokens for their own lookups). Because
    `UnicodeNormalizer` runs unconditionally over every column, including nullable ones already turned
    `None` by their own `NullTokenNormalizer`, plan 06-11 Task 2's `None`-passthrough guard is what
    keeps this call from raising `TypeError` on those columns — do not remove or weaken that guard when
    wiring this stage list.

    Update `StagingLoader.load()`'s single `stages=[RaggedRowGuard()]` literal to
    `stages=self._build_stages(ctx)`. Update this file's module docstring to name the normalizers it
    now threads through `run_streaming`, to state explicitly that `_record_hash` (computed
    immediately after this loop, unchanged in this task) is therefore computed over NORMALIZED values
    — the hard ordering edge ROADMAP's plan guidance names ("normalization MUST precede hashing") now
    holds in the real pipeline, not merely in each normalizer's own isolated unit test — and to state
    the nullable-column ordering rule (`NullTokenNormalizer` before its column's type-specific
    normalizer) as a documented invariant, not an implementation accident.
  </action>
