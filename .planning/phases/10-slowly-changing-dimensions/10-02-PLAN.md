      carries the SAME birth_date value, taken from the row with the MAXIMUM event_ts across the
      WHOLE history (ties broken by the highest source_row_number) -- proving Type-1 has no
      per-version history at all, even retroactively.
    - Test 4 (Type-0, SCD-01): a history where `signup_country` differs across rows -- EVERY
      resulting version row carries the value from the row with the MINIMUM event_ts (ties broken
      by the LOWEST source_row_number); any other row's signup_country value is provably ignored
      (assert changing a later row's signup_country does not change the output at all).
    - Test 5 (identical event_ts tie-break -- Assumption A2's named edge case): two rows sharing
      the EXACT same event_ts but different source_row_number values and different (name,
      country) -- the function does not raise, does not silently drop a row, and orders them by
      source_row_number ascending as the deterministic tie-break, producing 2 distinct versions
      (not 1) since the tracked hash genuinely differs.
    - Test 6 (NULL-safety, Pitfall 5's class): a history where an early row's `country` is `None`
      and a later row's `country` is a real string -- this MUST be detected as a version boundary
      (NULL IS DISTINCT FROM 'PL' is TRUE), never silently treated as "no change" the way a naive
      `==` comparison would mishandle it.
    - Test 7 (surrogate-key independence, SCD-04): the function's output (VersionRow) carries NO
      surrogate/identity value at all -- prove this structurally by asserting VersionRow has no
      `id` field; the surrogate key is assigned later, by the database's own Identity column, only
      at INSERT time -- recompute_version_chain has no opinion on it and cannot influence it.
    - Test 8 (schema-version-change irrelevance -- RESEARCH.md Open Question 3): a history where
      some rows carry an EXTRA, unrelated field (simulating a schema-evolution column like
      loyalty_tier) that this function's BronzeRecord type does not even have a slot for --

      output to an otherwise-identical history without it, proving schema evolution on untracked
      columns can never spuriously trigger a new SCD2 version.
  </behavior>

    [datetime], signup_country, source_row_number [int, the tie-break]) and `VersionRow` (frozen
    dataclass: customer_id, name, country, birth_date, signup_country, valid_from, valid_to,
    is_current -- deliberately no id/surrogate field, per Test 7). Implement
    `recompute_version_chain(history: Sequence[BronzeRecord], *, valid_to_sentinel: datetime) ->
    list[VersionRow]`: (1) sort history by (event_ts, source_row_number) ascending; (2) compute
    each row's tracked hash via `hashing.tracked_attribute_hash(row.name, row.country)`; (3) a new
    version group starts at index 0 and at any index i where hash[i] is NULL-safely distinct from
    hash[i-1] (Python: `hash_i != hash_prev` is already NULL-safe for bytes/None in Python
    semantics, but document explicitly why this differs from SQL's three-valued logic -- Python's
    `!=` on two `None`s is `False` and on `None`/bytes is `True`, which is exactly IS-DISTINCT-FROM
    semantics, so no special-casing is needed here, only in SQL contexts); (4) each version's
    name/country = the value of the FIRST row in its group; valid_from = that first row's
    event_ts; valid_to = the NEXT version's valid_from, or `valid_to_sentinel` for the last group
    (is_current=True only for the last group); (5) compute `latest_birth_date` = birth_date of the
    row with max (event_ts, source_row_number) across the WHOLE history, and
    `earliest_signup_country` = signup_country of the row with min (event_ts, source_row_number)
    across the WHOLE history -- apply both to EVERY emitted VersionRow uniformly. Return the list
    of VersionRow, oldest version first.
