<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Alembic migration → analytical PostgreSQL | DDL executes with whatever privilege the connecting role holds; the wrong-database guard is the boundary that prevents it executing against the wrong database entirely |
| `etl_app` → the six tables | the application role's entire privilege surface is defined by these GRANT statements — there is no other place this grant is issued |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-04 | Elevation of Privilege | every migration's GRANT statement | mitigate | Per-table `GRANT SELECT, INSERT, UPDATE`, never `GRANT ALL` or schema-wide; `test_etl_app_grants` asserts the exact privilege set per table, catching a future migration that widens it |
| T-03-07 | Tampering | `migrations/env.py` connecting to the wrong database | mitigate | The wrong-database guard (`current_database()` check) fails before any DDL runs; this is the mechanism, not merely a convention |
| T-03-08 | Tampering | SQL injection via dynamic identifiers in `op.execute(...)` | accept | Every schema/table identifier in this phase's migrations is a static Python string literal, never user- or config-derived; no dynamic identifier construction exists in this plan's scope |
</threat_model>
