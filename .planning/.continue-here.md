## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| Premature debug-session closure on offline-only evidence | A fix proven correct in an isolated/synthetic reproduction was treated as sufficient to close a live-environment bug report, without ever confirming it against the actual live failure. | blocking | Before marking any live-environment (E2E/CI) debug session RESOLVED, require at least one live CI run that actually reaches the originally-failing assertion and passes — not just an offline/unit/integration proof. If live confirmation is infeasible after genuinely repeated attempts, the session may close on offline evidence alone, but MUST say so explicitly in its Resolution (as `rebuild-scd2-reconciliation.md`'s member-32 fix currently does) rather than silently treating offline proof as equivalent. |
| Forgetting to re-arm live-run watchers after each dispatch | On at least two occasions this session, the coordinator said "I'll re-arm the fallback poller" and then did not actually call the Monitor tool for the new run ID, leading to CI runs finishing hours before anyone noticed. | advisory | When dispatching or being notified of a new live CI run, immediately verify a Monitor/watcher task actually exists for that exact run ID (not just intend to create one) before moving on. |
| Budget-raise as first response to a timeout failure | Several early rounds treated "test X times out" as "test X's timeout is too short" and raised the number, before getting direct evidence of the actual blocking mechanism. This repeatedly wasted a ~2-4 hour CI cycle per guess. | advisory | Get direct TI/pod-log/scheduler-log evidence for *why* something is slow or stuck before changing any timeout/retry number. This session's later rounds (20+) adopted this discipline consistently and it paid off — keep doing it. |
